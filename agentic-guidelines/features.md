# Describes naming & functionality guides to develope features referenced on sections.md

## manageUserUnknow

Gestiona el acceso gratuito por perfil de navegador mediante una cookie opaca persistente, `HttpOnly`, `SameSite=Strict`, `Secure` en producción y `Path=/api`. El servidor guarda solo el hash del token y mantiene dos contadores independientes: hasta 3 evaluaciones de ideas y hasta 3 envíos de roast por perfil. El perfil se elimina tras 400 días sin actividad, por lo que el cupo puede volver a empezar al crearse un perfil nuevo. Se aplican a visitantes sin cuenta y también a cuentas autenticadas que no tengan activo el plan correspondiente; contratar un plan distinto no elimina ni consume el cupo gratuito del otro ámbito. No hay reinicio por sesión, día, semana ni mes; no se guarda historial personal anónimo, IP en claro, texto de ideas ni insultos para aplicar estos límites.

La cookie identifica un perfil, no una persona. Borrar cookies o cambiar de navegador/dispositivo puede crear una identidad nueva; sin cuenta o identificación más invasiva no se puede prometer un límite por persona. La IP es una señal secundaria para rate limiting y detectar rotación abusiva de identidades. No es clave de identidad ni causa un bloqueo permanente: redes compartidas, VPN y cambios de dirección pueden afectar a personas distintas. No se usa fingerprinting de navegador.

Las reservas de cuota son atómicas e idempotentes. La API comunica cupo disponible; el frontend solo lo presenta. Una evaluación de idea válida consume una unidad. Detectar una idea repetida y mostrar el aviso no consume; «Evaluar igualmente» reserva y consume una unidad si la evaluación termina correctamente. Un error libera la reserva. Un rechazo posterior a continuar no suma otro uso ni otro registro de idea repetida. Un envío de roast consume una unidad cuando obtiene una respuesta válida. El resultado idempotente se conserva hasta 24 horas para responder reintentos sin duplicar consumo; no constituye historial.

El cupo gratuito agotado devuelve `429` con código estable y cero usos restantes; no incluye `Retry-After` porque el límite no se reinicia. La UI comunica si muestra intentos gratuitos o intentos diarios de un plan. Para cuentas, Iluminado permite 11 evaluaciones diarias y Faltón 11 roasts diarios mientras la suscripción correspondiente esté vigente; cuando falta el plan de ese ámbito, la API aplica el cupo gratuito del perfil de navegador. Al agotarse ese cupo devuelve `429 ANONYMOUS_QUOTA_EXHAUSTED`; al agotarse el cupo diario de un plan vigente devuelve `429 PLAN_QUOTA_EXHAUSTED` con `scope` y `remaining: 0`. El contador de cuenta comunica el reinicio diario; la petición llega a la API para que el servidor aplique el límite. Las cuotas y contadores nunca se aceptan desde el navegador como autoridad.

La ruta de roast está mediada por API y consume el cupo del servidor correspondiente al estado del plan. El backend limita la creación a 20 perfiles por IP cada 24 horas con HMAC, y limita ideas/roast a 10 solicitudes por minuto y la API general a 120 por IP/minuto. Las reglas de retención están en [uso anónimo](../doc/anonymous-usage.md).

## getUserIdea

This only captures the text content from `IdeaInput`. It can be added by the user in three ways:

- pasting text from clipboard,
- writing with device's keyboard
- using device's microphone. In this case we have to call transcriptUserIdea

En Home, el contenedor `GetUserIdea` presenta la captura en dos pasos. El
primero muestra el campo de texto y «Adelante»; esa acción valida entre 10 y
2.000 caracteres y solo avanza a la selección de tono, sin llamar a la API ni
consumir intentos. El segundo paso permite elegir `soft` o `hard` y ofrece
«Evaluar idea», que envía `ideaText` y `tone` al flujo `evaluateIdea`. «Cambiar
idea» vuelve al campo conservando el texto y el tono seleccionado. Al cambiar
de paso, el foco se mueve al primer control interactivo de la nueva vista.

La Home may show a brief, temporary client-side synthesis beside the mascot while the idea is being written. This preview is presentation only: it is not evaluated, sent, or persisted.

## transcriptUserIdea

Forma parte de la primera entrega. Solicita permiso de micrófono, transcribe temporalmente y vuelca el texto en `IdeaInput` para revisión antes del envío. Si falla o se deniega el permiso, conserva el texto existente y permite escribir. No se persiste el audio.

- El contenedor `TranscriptUserIdea` vive en `features/transcript-user-idea/`; el adaptador `shared/utils/speech-to-text.ts` es compartido porque la transcripción de roast también lo utilizará.
- La transcripción se concatena al texto editable, respetando el límite de 2.000 caracteres. No se envía ni se persiste desde este flujo.
- Solo se usa reconocimiento en el dispositivo (`processLocally = true`) en `es-ES`. La aplicación comprueba la disponibilidad del modelo local y puede instalar el paquete de idioma en el dispositivo; nunca recurre al reconocimiento remoto. El control se oculta en Android, donde no se considera suficiente la presencia de la API para garantizar el modo local. Si el navegador no expone la API local necesaria, se oculta el control y la escritura manual sigue disponible. Si la API existe, pero el paquete local no está disponible o se deniega el permiso, se muestra un error sin borrar el texto y no se inicia el dictado.
- Los errores se reducen a categorías seguras (`unsupported`, `local-unavailable`, `permission-denied`, `no-speech`, `failed`); no se muestran mensajes crudos del navegador.

## getIdeaListWorstAllTime

Implementado como endpoint público `GET /api/worst-ideas/all-time` y consumido por `WorstIdeasAllTime` antes del ranking semanal. Devuelve como máximo diez `{ safeTitle, count }`, ordenados por count descendente y `safeTitle` ascendente. El agregado conserva solo título seguro y cantidad después de que el corpus semántico purgue la idea a los 24 meses de inactividad; también se elimina cuando `last_received_at` supera ese plazo. La migración `032_worst_ideas_all_time_ranking.sql` retrocarga únicamente ideas que todavía estén en el corpus al aplicarse; no reconstruye las que ya se purgaron. Comparte el límite dedicado de 30 solicitudes por minuto e IP con el ranking semanal, además del límite general; los contadores son locales al proceso.

## getIdeaListWorstAll

Implementado en la API como endpoint público `GET /api/worst-ideas` y consumido por el componente `WorstIdeasAll` de la ruta `/lo-peor-de-lo-peor`. Devuelve como máximo 10 `IdeaListItemWorstAll` de la semana ISO actual en `Europe/Madrid`, ordenados por cantidad semanal descendente y título seguro ascendente como desempate. El score de rúbrica no influye en la posición. La respuesta incluye solo `safeTitle` y `weeklyCount`; nunca autor, embedding ni texto original. El score conceptual se persiste con el rechazo, pero no forma parte de la respuesta ni del orden del ranking. El endpoint tiene un límite específico de 30 solicitudes por minuto y dirección IP, además del límite general de 120 por minuto; ambos contadores son locales al proceso y no se comparten entre réplicas. La UI valida la respuesta en ejecución y presenta carga, error con reintento, lista vacía o ranking.

## getIdeaListWorstUser

Implementado como endpoint privado `GET /api/account/worst-ideas`, consumido por el componente `WorstIdeasUser` de `/lo-peor-de-lo-peor`. `AccessTokenGuard` exige una sesión activa; el controlador obtiene el propietario exclusivamente de `request.user.userId`, nunca de parámetros ni del cuerpo de la solicitud. Devuelve como máximo 10 elementos `IdeaListItemWorstUser` con `{ safeTitle, count }`: una fila por idea rechazada canónica atribuida a esa cuenta, ordenada por recuento descendente y `safeTitle` ascendente. El recuento refleja las recepciones del usuario para esa idea; envíos autenticados nuevos y coincidencias semánticas lo incrementan dentro de la misma transacción que actualiza el registro común, con idempotencia por envío. No incluye autor, texto original, score, embedding ni ID interno. El endpoint tiene un límite específico de 30 solicitudes por minuto y dirección IP, además del límite general de 120 por minuto; ambos contadores son locales al proceso y no se comparten entre réplicas. Los visitantes anónimos no generan historial personal; la UI trata un `401` como estado sin sesión e invita a crear una cuenta. Si no hay ideas muestra un estado vacío distinto; fallos de carga permiten reintentar. La migración `018_user_rejected_ideas.sql` no retrocarga rechazos anteriores: el historial individual empieza a acumularse con el seguimiento autenticado habilitado.

## searchSimilarIdea

`searchSimilarIdea` crea con OpenAI una firma semántica neutral y efímera de la idea y la convierte con `text-embedding-3-small` (1536 dimensiones) en un vector. Pgvector recupera hasta 20 candidatas rechazadas más cercanas, sin un umbral coseno fijo. `gpt-5.4-mini` compara la idea original y la firma con los títulos seguros y solo confirma coincidencia cuando coinciden finalidad y público/objeto (`sameIdea: true`). El vector selecciona candidatas; el comparador decide equivalencia. Las firmas no se guardan y las llamadas a Responses usan `store: false`. Busca solo ideas rechazadas y no consulta ni reutiliza evaluaciones, puntuaciones ni veredictos previos. Una idea aprobada no se agrega al corpus de similitud ni activa el aviso de repetición; si la persona está autenticada, su título privado se guarda por separado en `approved_ideas` para su perfil.

Al encontrar coincidencia, `updateWorstIdea` incrementa el contador agregado de esa idea inmediatamente, aunque la persona no continúe, y la UI muestra el título seguro, el contador total actualizado y una frase valorativa acorde al tono seleccionado. El envío lógico se cuenta una sola vez: si la persona continúa y la evaluación vuelve a rechazar la idea, no se incrementa otra vez. La continuación reutiliza la clave de idempotencia original, válida durante 24 horas, y el servidor permite una sola continuación simultánea. La UI ofrece una acción explícita para evaluar igualmente. Las cuentas autenticadas con Iluminado reservan un intento diario en el servidor; mostrar solo el aviso no lo consume y «Evaluar igualmente» lo confirma al terminar con una respuesta válida. Si falla la evaluación de la continuación antes de guardar el resultado, se liberan la reserva de uso y el claim para permitir reintentar con la misma clave; se conserva la coincidencia ya registrada y no se repite su incremento.

`manageUserUnknow` controla el cupo de hasta 3 evaluaciones por perfil anónimo, que se purga tras 400 días sin actividad y reserva un uso al continuar después de una coincidencia. Las cuentas autenticadas pasan por el guard de sesión y consumen la cuota diaria de Iluminado con validación server-side de la suscripción vigente. El uso anónimo y el autenticado se mantienen independientes.

Sin coincidencia, se ejecuta `evaluationProcess`. Si el veredicto final es `RECHAZADA`, la respuesta estructurada incluye `safeTitle`; un verificador independiente lo valida antes de que la orquestación invoque `addToWorstIdeas` para añadir título, embedding y contador inicial `1`. Si el verificador falla, no se guarda ni publica la idea. Otros veredictos no se añaden al índice. La ruta de escritura del corpus de rechazo no persiste el texto original; la excepción acotada para diagnosticar errores 5xx de evaluación se describe en la sección del panel admin.

Cuando la decisión es `SIN_BLOQUEO_EVIDENTE` y la petición lleva un access JWT válido, se guarda en `approved_ideas` un título privado derivado de la idea y vinculado a `request.user.userId`. Visitantes anónimos no crean historial. SHA-256 del `Idempotency-Key` evita una segunda fila por reintento; el título aprobado no se publica ni se incorpora al índice de similitud. Si la escritura falla, la API no devuelve éxito y registra solo un código de error.

La búsqueda incrementa el contador al detectar match, incluso si no se continúa; la operación es idempotente por petición lógica durante 24 horas. Título, embedding y contador caducan a los 24 meses de la última recepción; las consultas ya excluyen filas caducadas, pero falta automatizar la eliminación física. La clave OpenAI se configura en `OPENAI_API_KEY` y nunca se incluye en Git. El aviso muestra el título seguro y el total actualizado. El diseño y las limitaciones están en [plan de seguridad y similitud](../doc/security-and-similarity-roadmap.md).

## evaluationProcess

La especificación funcional, el contrato, la rúbrica y el plan TDD de esta feature están en [scoring-viability-software.md](./scoring-viability-software.md). Ese documento sustituye las instrucciones anteriores de `evaluationProcess` de este archivo.

## showEvaluationResults

Presenta score conceptual global (0–10, dos decimales), un titular propio de Grumphya y una explicación concreta que reúna los aspectos mediocres evaluados y el defecto decisivo. El titular cambia entre `soft` y `hard`; la explicación permanece en lenguaje sencillo y nunca expone códigos internos como `C05`, `C10` ni los aliases de la rúbrica. Si alguno aparece en la respuesta del modelo, la API lo sustituye por una descripción comprensible del aspecto evaluado. El modelo no recibe el tono: este no cambia la evaluación ni el score. La interfaz no presenta el defecto como «bloqueo». Sin fallo estructural evidente, el score es la media de criterios puntuados dividida entre 10; el filtro C10 de diferenciación en categorías maduras siempre se puntúa para que una idea funcional no quede sin nota; insuficiente devuelve `null`. Si el primer veto del rechazo es C10 (`stop_at: C10`) y el modelo conoce con alta confianza un producto con las mismas funciones esenciales, la interfaz puede mostrar su nombre bajo «Ejemplo conocido con funciones similares:»; no hay búsqueda web ni verificación de disponibilidad actual y el nombre no afecta al resultado. El contrato completo está en `scoring-viability-software.md`.

## registerWithPlan

Feature `features/register-with-plan/`, con contenedor `RegisterWithPlan`. Solo se crea una cuenta al elegir Iluminado o Faltón; el uso anónimo gratuito no requiere registro.

### Flujo y contrato

1. En precios, un visitante sin sesión que elige un plan envía `POST /api/registration-intents` con el código de plan. El servidor valida que sea contratable, crea una intención opaca, de un solo uso y corta duración (15 minutos), y la vincula a una cookie `HttpOnly`, `Secure` en producción, `SameSite=Strict` y `Path=/api`. La URL posterior es `/crear-cuenta` y no contiene plan, token ni datos de contratación. Un usuario ya autenticado que elige cualquier plan es dirigido a `/perfil` para contratar el plan inactivo. Abrir `/crear-cuenta` con sesión activa también redirige a `/perfil`. El plan del alta se recupera exclusivamente de la intención guardada en servidor. La intención caducada, consumida o ausente obliga a volver a precios.
2. La creación de intención y el alta son operaciones mutables: validar `Origin` contra el origen esperado, exigir JSON y aplicar protección CSRF apropiada además de `SameSite`; no confiar solo en la cookie. El identificador de cookie debe ser aleatorio, no contener datos y almacenarse como hash cuando se persista. No aceptar del navegador precio, vigencia, permisos ni estado de pago.
3. `POST /api/registrations` valida `email`, `username`, `password` y `privacyPolicyAcknowledged: true`, consume la intención e inserta la cuenta pendiente con el hash SHA-256 de un token de verificación aleatorio. No crea aún sesión, suscripción, compra ni cuota. La contraseña se guarda como bcrypt cost 12 sobre su prehash SHA-256 hexadecimal. El servidor registra versión y fecha de la política presentada; el booleano no es consentimiento genérico ni sustituye la base jurídica del tratamiento. Email, alias, contraseña y token no se escriben en logs.
4. La API envía un correo HTML y texto plano con un enlace de un solo uso, válido 24 horas, a `/verificar-cuenta#<token>`. El fragmento no se envía en la petición HTTP inicial; la página lo lee y lo elimina de la barra de direcciones, pero no consume el token al abrirse. Presenta el botón «Confirmar correo» y solo tras esa acción explícita envía `POST /api/registrations/verify`, que consume el enlace y crea un permiso temporal de confirmación de 15 minutos. La UI presenta entonces la contratación simulada para confirmación explícita. Solo `POST /api/registrations/confirm` activa cuenta, suscripción, compra, cuotas y sesión; no se procesa dinero real. El refresh se entrega en cookie `HttpOnly`.
5. Si la entrega del enlace falla, la cuenta permanece pendiente y se puede solicitar reenvío desde la pantalla de confirmación. La respuesta de reenvío es genérica; cada reenvío rota el token y aplica espera y máximo por cuenta, además del límite por IP. En desarrollo sin SMTP se conserva una vista previa local en memoria; no se envía un correo. `GET /api/dev/mail-preview/latest` no existe en producción.
6. `GET /api/account/profile` exige `Authorization: Bearer <access JWT>` y obtiene el usuario exclusivamente de `request.user.userId`; devuelve sus datos y el estado de ambos planes, además de `avatarUrl` nullable. Los planes inactivos muestran 0 intentos. Los activos muestran el cupo diario del plan menos el uso persistido para la fecha de `Europe/Madrid`. `GET /api/account/good-ideas`, con la misma autenticación, devuelve `{ ideas: [{ id, title, createdAt }] }` para el propietario, con las diez más recientes en orden descendente; nunca acepta `userId` del cliente. El perfil muestra la tabla solo cuando hay ideas aprobadas y presenta únicamente título y fecha. Los planes duran un mes desde la compra simulada y no se renuevan automáticamente. `POST /api/account/subscriptions/purchase` reactiva un plan inactivo con una compra simulada idempotente; el servidor impide una compra duplicada mientras siga activo. El perfil ofrece «Pagar un café» solo para planes inactivos y reutiliza el diálogo de pago. No existe cancelación anticipada de planes.

### Validación, privacidad y abuso

- Email: máximo 254 caracteres; quitar espacios exteriores, normalizar dominio y comparar toda la dirección sin distinción de mayúsculas. No eliminar puntos ni sufijos particulares de proveedores. Validar sintaxis en servidor y cliente. La sintaxis inválida puede responder con el mensaje: «Venga ya, ese correo no es de verdad, escribe bien anda.»
- Alias: entre 3 y 30 caracteres; permitir letras/números Unicode y `_`, `.` o `-` solo entre caracteres alfanuméricos. Quitar espacios exteriores, normalizar Unicode NFC y aplicar unicidad sin distinción de mayúsculas con una regla estable. Rechazar controles y caracteres invisibles engañosos. El alias reservado de administración `jappy` se rechaza en el alta pública sin distinguir mayúsculas/minúsculas; el registro y el bootstrap consultan la misma constante. Mantener por separado el alias normalizado y el de presentación.
- **Implementado:** contraseña de 12–128 caracteres, con mayúscula, minúscula, número y carácter que no sea letra, número ni espacio; no se recorta ni normaliza silenciosamente y se rechazan controles. Los hashes nuevos usan bcrypt cost 12 sobre SHA-256 de la contraseña UTF-8 convertido a hexadecimal. El prehash evita el límite de 72 bytes de bcrypt; el valor original nunca se almacena ni registra. Los hashes heredados `scrypt` se siguen verificando y se actualizan a bcrypt después de un login válido mediante compare-and-set; no se fuerza un cambio de contraseña ni hay migración de esquema. SHA-256 para hashes de tokens y HMAC-SHA-256 para firmas son mecanismos distintos y no se cambian como parte de la migración de contraseñas.
- Si email o alias ya existen, devolver exactamente el mismo estado HTTP, `code` y cuerpo genérico en ambos casos; no distinguir cuál campo coincide. El registro queda pendiente mientras exista una alta pendiente con esos datos. El reenvío de verificación usa respuesta genérica y duración mínima para reducir enumeración; los límites de intentos se aplican en servidor.
- La casilla empieza desmarcada y es obligatoria. El texto «He leído la política de privacidad» enlaza claramente a `/politica-de-privacidad`; un texto auxiliar permite consultar `/terminos-y-condiciones` de forma separada, sin añadir una aceptación contractual al formulario. Sin marca, el formulario no se envía y la API también rechaza la petición con un error claro y accesible. La ruta de privacidad muestra la versión 4. Las nuevas altas registran `v4`; las aceptaciones existentes conservan la versión anterior mientras no se solicite una nueva. Este acuse de lectura no equivale al consentimiento opcional para rankings, que se gestiona y revoca por separado desde el perfil.
- El CTA de alta comunica la contratación simulada por un mes. El panel lateral aclara que el plan no se renueva automáticamente y que para contratar otro mes hay que volver a hacerlo. La activación es simulada: no se procesa dinero real.
- **Implementado en API:** middleware por IP/proceso y ventana de un minuto limita la API general a 120 solicitudes, creación de intención a 20, alta a 8 y verificación/confirmación/refresh a 10; los endpoints de evaluación tienen además su límite propio. Al superar el límite responde `429` y `Retry-After`. El parser JSON limita el cuerpo a 8 KB. La UX específica de `429` debe verificarse con las pruebas integradas. Los límites no son configurables, se reinician con el proceso y no se comparten entre réplicas; antes de producción multiinstancia deben trasladarse a almacenamiento compartido o gateway. No hay baneos por IP ni detección de automatización.
- **Sanitización/validación:** email y alias se normalizan/validan en el servicio del backend; la API recibe datos como `unknown` y valida su forma. Las rutas actuales no contienen parámetros sensibles de registro. Mantener validación por lista permitida y límites de tamaño para cualquier parámetro de ruta/query futuro; codificar al presentar texto y nunca interpolar entrada en HTML/SQL/URLs. Sanitizar no sustituye validación contextual ni consultas parametrizadas.
- **Doble envío:** una referencia bloquea sincrónicamente los submits tras el primer envío válido, el botón se deshabilita durante la petición y el estado de procesamiento bloquea nuevos envíos tras aceptación. La cuenta pendiente no recibe permisos ni sesión; la verificación y activación de cuenta, suscripción, compra simulada, cuotas y sesión se completan transaccionalmente al confirmar. Un conflicto o fallo no debe conceder permisos parciales.
- No registrar contraseñas, tokens, emails completos, alias, contenido de ideas ni enlaces de verificación. Usar logs de evento con códigos de error y métricas agregadas.

`/terminos-y-condiciones` muestra el resumen sobre tratamiento de ideas y dictados que se retiró de Home. Es una ruta distinta de `/politica-de-privacidad`, que muestra la versión 4 vigente. Antes de producción, comprobar contratos y ajustes reales de proveedores, copias, logs y garantías para menores descritos en `doc/privacy-policy-assessment.md`.

### TDD y criterios de aceptación

- Las pruebas cubren plan ausente/no permitido, intención caducada/reutilizada, CSRF/origen inválido, sintaxis de email inválida, política no marcada, límites de campos y grupos de contraseña ausentes, además de `429` y doble submit.
- Con concurrencia, dos altas con la misma identidad producen como máximo una cuenta por las restricciones únicas de base de datos. Email duplicado y alias duplicado producen la misma respuesta HTTP/código/cuerpo; comprobar que las respuestas no revelan qué campo ya existe.
- El hash de contraseña es verificable con el algoritmo configurado; el valor original y los tokens no aparecen en base de datos ni logs. La intención es de un solo uso y caduca según servidor.
- La creación de alta pendiente no genera suscripción, compra, cuotas ni sesión. Abrir la página del enlace no consume el token: la persona debe pulsar «Confirmar correo» para que la UI envíe la verificación. El token se consume una sola vez y caduca a las 24 horas; el permiso temporal para confirmar dura 15 minutos. La confirmación activa suscripción, compra simulada, cuotas y sesión en la misma transacción. Un fallo no deja permisos parciales. El perfil requiere sesión válida; las suscripciones vencen al mes y no se renuevan automáticamente.
- La cuota diaria es 11 en el ámbito del plan activo y 0 en el otro; el plan inactivo registra 0 intentos. Evaluaciones exigen Iluminado vigente y roasts Faltón vigente. El reinicio diario usa la fecha de `Europe/Madrid`; reserva y consumo se coordinan en PostgreSQL y son idempotentes.
- Prueba E2E aislada: seleccionar plan → URL limpia → validar privacidad y formulario → pantalla de correo pendiente → verificar enlace → confirmar contratación simulada → perfil con plan/intentos y datos de la cuenta → baja persistida; cubrir duplicados, expiración, reenvío, sesión inválida y que ningún fallo conceda permisos.

## userAvatar

La persona autenticada puede editar su avatar desde el perfil mediante un diálogo: el avatar actual y las imágenes públicas se muestran en círculo; dentro del editor se puede elegir JPEG, PNG o WebP, arrastrar y ajustar el encuadre con zoom de 1× a 3× y desplazamiento horizontal/vertical, con una previsualización circular. El navegador prepara el recorte en canvas como JPEG de 128 × 128. `POST /api/account/avatar` conserva el contrato de una sola parte multipart llamada `avatar`, exige Bearer válido y `Origin` exacto de `WEB_ORIGIN`, y limita el archivo a 5 MiB. El middleware limita la ruta a tres subidas por minuto usando `request.ip` en cada proceso. `main.ts` no confía en proxies por defecto. La caja Compose de producción habilita solo la IP fija de Caddy (`172.31.0.254/32`); la API no publica puertos. Si cambia la topología, actualiza esta allowlist para que incluya únicamente los proxies conocidos y nunca confíes en `X-Forwarded-For` arbitrario. El backend vuelve a validar el formato rasterizado decodificado y su correspondencia con el MIME declarado; rechaza SVG y formatos disfrazados. Sharp limita la entrada a 20 megapíxeles, normaliza orientación, convierte el resultado a WebP de 128 × 128 con calidad 82 y descarta metadatos y bytes originales. El círculo es una máscara visual; la imagen persistida sigue siendo cuadrada.

La API envía el WebP final procesado a OpenAI `omni-moderation-latest` con la clave `OPENAI_API_KEY` ya configurada, solo desde servidor. Ni el archivo original ni el JPEG temporal del navegador se guardan. Una imagen marcada se rechaza; si falta la clave, vence el timeout de 10 segundos, el proveedor falla o el cuerpo no cumple el contrato, se responde error cerrado y no se persiste la carga. El frontend informa que OpenAI recibe la imagen para una comprobación automática y que el avatar será visible junto al alias en áreas públicas. La moderación reduce riesgo, pero puede equivocarse y no garantiza que todo contenido inadecuado sea detectado. No es una clasificación legal por edades ni moderación humana; no está diseñada para detectar CSAM y no deben cargarse imágenes conocidas o sospechosas de esa categoría.

Los errores de carga se exponen con respuestas saneadas: `400` para archivo o multipart inválidos, `413 AVATAR_TOO_LARGE` para superar 5 MiB y `503` genérico ante fallos del moderador, almacenamiento o actualización de cuenta. Las respuestas no exponen rutas, claves de almacenamiento ni detalles internos.

La tabla `users` guarda solo una clave aleatoria UUID con sufijo `.webp`. Los archivos residen fuera del web root con permisos restrictivos, en `USER_AVATAR_DIRECTORY` (por defecto `var/avatars`). Compose los persiste en el volumen `grumphya-avatar-data`; recrear servicios conserva fotos y datos SQL. `GET /api/avatars/:avatarKey` es público para permitir su presentación, valida el formato UUID, devuelve `image/webp`, `no-store` y `nosniff`, y no revela ID ni ruta de almacenamiento. `getUserProfile` entrega `avatarUrl` nullable. Las listas públicas Roast y Best Users pueden incluir este avatar, así que elegirlo implica publicación junto al alias. Reemplazar el avatar elimina el archivo anterior. La baja física elimina el avatar y la fila SQL; si la transacción SQL falla, el repositorio intenta restaurar la copia del archivo y registra sin datos personales si la restauración también falla.

El endpoint requiere la clave existente: sin `.env`/OpenAI configurado el perfil puede cargarse, pero no se aceptan nuevas imágenes. La versión 4 de `/politica-de-privacidad` describe la moderación y publicación del avatar. Confirmar el contrato y la configuración efectiva de proveedores antes del despliegue público.

## submitRoast

El usuario envía a `POST /api/roast` un mensaje de hasta 400 caracteres y una `Idempotency-Key` UUID. La API pide a OpenAI una respuesta breve en español bajo un esquema JSON estricto; la petición usa `store: false` y un timeout abortable de 10 segundos. Se permiten insultos y palabrotas en el mensaje recibido, pero la respuesta debe desarmarlo con humor sencillo, sin insultar explícitamente, usar palabrotas ni atacar a terceros. Las instrucciones piden una sola frase de hasta 200 caracteres, con palabras cotidianas y un chiste claro sobre un detalle concreto e inocuo del mensaje; prohíben frases genéricas, metáforas enrevesadas, frases grandilocuentes, palabras rebuscadas y citas literales. No debe incluir datos personales, credenciales ni información sensible, aunque aparezcan en el mensaje. El servidor valida la estructura, el máximo de caracteres y el lenguaje explícitamente abusivo; la claridad y la alusión concreta dependen del modelo y no tienen una validación semántica automática. Si el proveedor excede el timeout, falla o produce una salida inválida, se libera la reserva. El mensaje original no se guarda como historial. Por ejemplo, ante «Me da pereza ordenar mi idea, pero creo que con una app se arregla», Grumphya podría contestar «Tu idea todavía está en pijama y ya quiere que una app le haga la cama».

Los visitantes y las cuentas autenticadas sin Faltón vigente conservan hasta tres envíos gratuitos por perfil de navegador, que se purga tras 400 días sin actividad. Con Faltón vigente la cuenta dispone de 11 envíos al día y ese uso no consume el cupo gratuito. El servidor reserva y consume la cuota correspondiente de forma idempotente; solo confirma el uso después de obtener y validar una respuesta. Si OpenAI falla o la respuesta no cumple las reglas, libera la reserva. El frontend presenta los intentos restantes, pero nunca decide los permisos. Las ideas, mensajes y respuestas de roast no se almacenan como historial personal.

La tabla `users` conserva `roast_messages_sent`, contador acumulado para cuentas autenticadas con Faltón vigente o con una suscripción Faltón activa anteriormente. Se incrementa al confirmar un envío válido incluso si esa cuenta usa su cupo gratuito de roast, y no vuelve a aumentar en reintentos idempotentes. No se reinicia con el límite diario ni guarda el contenido del mensaje; `getRoastRanking` lo utiliza para ordenar el ranking público.

## getRoastRanking

`GET /api/roast-ranking` devuelve hasta diez cuentas activas con consentimiento de ranking, ordenadas por `roast_messages_sent` descendente y por nombre de usuario ascendente en caso de empate. El resultado expone `username`, `roastMessagesSent` y `avatarUrl` opcional; no incluye IDs ni correos. El consentimiento se guarda mediante `POST /api/account/privacy/rankings`, está desactivado por defecto y se puede revocar desde el perfil. El endpoint tiene un límite dedicado de 30 solicitudes por minuto e IP además del general de 120; ambos contadores son locales al proceso y no se comparten entre réplicas. Solo aparecen cuentas con consentimiento de ranking activo; si no hay participantes con consentimiento, devuelve una lista vacía.

## getBestListBestUsers

`GET /api/best-users` devuelve como máximo diez cuentas activas con consentimiento de ranking, ordenadas por cantidad de ideas aprobadas descendente y alias ascendente para desempatar. El componente `BestUsers` de «Humanos notables» destaca el primer puesto y conserva el formato de clasificación del prototipo. El DTO incluye alias, número de aprobaciones y `avatarUrl` opcional; no expone títulos, resúmenes ni evaluaciones de ideas. El endpoint tiene un límite dedicado de 30 solicitudes por minuto e IP, además del límite general; ambos contadores son locales al proceso y no se comparten entre réplicas.

`getIdeaListWorstAllTime` y `getIdeaListWorstAll` exponen dos rankings públicos en `/lo-peor-de-lo-peor`: el histórico aparece primero y el semanal después, con el mismo formato. Ambos muestran solo título breve seguro y cantidad de recepciones de ideas rechazadas (`reject`), sin usuario ni texto original. El endpoint histórico `GET /api/worst-ideas/all-time` devuelve hasta diez filas ordenadas por cantidad total descendente y título ascendente; conserva únicamente título seguro y contador agregado después de purgar el embedding y la fila del corpus, hasta que `last_received_at` alcanza 24 meses de antigüedad, momento en que también elimina el agregado. La migración inicial retrocarga solo las ideas que aún permanecen en el corpus; no recupera ideas purgadas antes de instalarse. El semanal `GET /api/worst-ideas` sigue limitado a la semana ISO actual. Ambos endpoints comparten el límite dedicado de 30 solicitudes por minuto e IP, además del límite general; los contadores son locales al proceso. Se excluyen nombres propios, datos personales, citas literales y detalles singulares que puedan identificar al autor. Si no puede generarse un título seguro, esa idea no entra en los rankings.

## evaluateIdea

Caso de uso principal del MVP.

- Entrada: `ideaText`, `tone` (`soft` o `hard`) y contexto de usuario.
- Valida longitud y tono en servidor. `manageUserUnknow` comprueba y reserva una cuota gratuita antes de realizar la evaluación. Una cuenta con Iluminado vigente reserva atómicamente el cupo diario; si no tiene ese plan, usa el cupo gratuito de su perfil de navegador, sin que otro plan contratado lo consuma.
- `IdeaSubmissionService` orquesta `searchSimilarIdea` antes de `evaluationProcess`; esta detección no lee datos de evaluación. Al coincidir, `updateWorstIdea` registra la recepción y la UI ofrece una acción explícita para continuar. Sin coincidencia, ejecuta `evaluationProcess`.
- `searchSimilarIdea` solo busca ideas previamente rechazadas. Una idea aprobada no se persiste ni entra en Worst Ideas; por eso no se detecta como repetida hasta que alguna evaluación la rechace.
- Tras un rechazo nuevo, invoca `addToWorstIdeas`; el embedding y el título seguro se guardan sin el texto original. Ninguna idea aprobada se incorpora al ranking.
- C07 también exige que la propia idea exprese un valor o motivo concreto para empezar y continuar usando el producto: una función que solo cuenta o registra una acción sin explicar qué problema resuelve ni qué resultado útil aporta suspende con `VALOR_USUARIO_NO_DEFINIDO`. No se exige evidencia externa de demanda ni que toda app resuelva un dolor; una finalidad explícita como bienestar, aprendizaje, comodidad o entretenimiento cuenta. La rúbrica C10 siempre puntúa una idea funcional, pero solo puede ser motivo de rechazo si la categoría es claramente madura y no hay un motivo reconocible para elegir la propuesta; antes se valoran los defectos concretos C01–C09 y no se rechaza por la mera existencia de alternativas. Si C10 es el motivo principal del rechazo, la explicación puede acompañarse de un nombre de producto solo si el modelo reconoce con alta confianza las mismas funciones esenciales; no se busca en la web ni se afirma disponibilidad actual. El nombre aparece en un campo independiente como contexto, no como afirmación de mercado, y no afecta a la evaluación. Una puntuación alta de C10 no compensa un suspenso de C07. Toda idea funcional completada recibe una puntuación numérica.
- La evaluación, persistencia, idempotencia de la recepción y cuotas anónimas y de cuenta están conectadas en la API. El evaluador real requiere configuración explícita.
- Salida del primer corte: estado, score conceptual, titular y explicación; contrato detallado en `scoring-viability-software.md`.
- Errores: entrada vacía, contenido no evaluable, límite agotado, proveedor de IA no disponible.

## Reglas de implementación

La captura de texto pertenece a `idea-input`; la evaluación pertenece a `idea-evaluation`. Ningún componente de interfaz decide puntuaciones, permisos o consumo de intentos.

## Criterios de aceptación

- Con la misma salida estructurada del evaluador y la misma versión de rúbrica, el score y el veredicto son deterministas.
- La disponibilidad se comprueba en servidor; un intento se reserva de forma atómica y solo se confirma con resultado válido. Los errores liberan la reserva. Un identificador de petición idempotente evita cobros dobles por reintentos de red.
- Una idea repetida incrementa su contador sin duplicar innecesariamente la evaluación.
- La respuesta diferencia datos, riesgos, supuestos y recomendaciones.
- En una sesión anónima no se crea historial personal. En una cuenta registrada, cada envío válido aparece en su historial, también si reutiliza una evaluación.
- Tests de borde v1: score `39/40/69/70`, dos criterios desconocidos, similitud `0,90` frente a un valor mayor, doble clic/reintento idempotente y reinicio del contador en medianoche de `Europe/Madrid`.

## submitContactMessage

El contenedor `SubmitContactMessage` reemplaza el formulario de demostración en `/contacto` cuando hay una sesión válida; cualquier cuenta autenticada puede enviar un asunto de 3–120 caracteres y un mensaje de 10–4.000 caracteres. `POST /api/contact-messages` acepta exclusivamente esos dos campos, toma el `userId` de `AccessTokenGuard` y los guarda en PostgreSQL asociados al usuario. Exige `Origin` exactamente igual a `WEB_ORIGIN` y `Content-Type: application/json`; devuelve `Cache-Control: no-store` y limita los envíos a cinco por minuto e IP, además del límite general. Los límites por minuto se guardan en memoria por proceso, no se comparten entre réplicas y se reinician al reiniciar la API. El asunto y texto del mensaje no se escriben en logs. Tras guardar, la API intenta enviar una confirmación SMTP con asunto genérico, fecha y referencia; no copia el contenido del mensaje. La UI diferencia entre enviado, vista previa local y fallo, y permite hasta tres intentos totales cuando el servidor autoriza reintentar. La bandeja privada de Jappy permite consultar hasta 100 mensajes recientes; no hay endpoints de lectura para usuarios normales. Jappy puede responder por correo a la dirección asociada a la cuenta; el destinatario se obtiene en servidor y el texto de respuesta no se almacena ni registra. Si el envío queda incierto, solo se permite un reintento tras confirmar la revisión del webmail. La aplicación no lee respuestas por IMAP. La tabla se purga a los 12 meses mediante `DataRetentionService`; la baja física de la cuenta también elimina los mensajes por cascada. La política de privacidad versión 4 informa de su finalidad y conservación; verificar ejecución y rotación de copias en producción. Los visitantes sin sesión mantienen el formulario de broma, sin envío ni persistencia.

## Administrador y métricas de operación

Jappy se aprovisiona de forma explícita e idempotente con el comando administrativo, usando `ADMIN_PASSWORD` solo en el servidor. Repetir el comando no cambia la cuenta; la rotación requiere `--change-password` y revoca las sesiones activas. Si el alias reservado ya pertenece a una cuenta normal, el aprovisionamiento falla sin promoverla. Las altas nuevas de Jappy reciben consentimiento de rankings públicos v2, revocable desde `/perfil`; la migración `033` concede ese consentimiento a la cuenta reservada existente si aún no lo tenía. El rol se consulta de nuevo en PostgreSQL al autorizar las rutas administrativas.

Solo la cuenta reservada Jappy (`role=admin` y alias normalizado `jappy`) puede evaluar ideas y enviar roasts sin plan ni límite diario; conserva las reservas idempotentes, pero no consume cuotas. Las evaluaciones aprobadas de Jappy cuentan para «Humanos notables» y sus roasts confirmados para «Faltón máximo» mientras mantenga el consentimiento público. Tras iniciar sesión, Jappy llega a `/panel-control`; el enlace aparece en la navegación de escritorio y móvil mientras el perfil autenticado tenga rol admin. Las rutas `/login` y `/crear-cuenta` también redirigen a `/panel-control` si la sesión corresponde a Jappy. Un visitante que abre `/panel-control` se redirige a `/login`; una cuenta normal se redirige a `/perfil`. La API protege `GET /api/admin/dashboard`, `GET /api/admin/application-errors/:eventId`, `GET /api/admin/contact-messages` y `POST /api/admin/contact-messages/:messageId/reply` con autenticación y comprobación del rol en PostgreSQL: responde 401 sin sesión y 403 sin rol admin. `/perfil` sigue mostrando los datos personales de Jappy; el panel tiene su propia ruta. El panel presenta ingresos simulados confirmados en EUR (cada compra guarda el precio vigente del plan) y coste de IA estimado en USD a partir de tokens devueltos por el proveedor. Las cifras semanales usan la semana natural de lunes a domingo en `Europe/Madrid`; el histórico empieza con la migración `023`, no se reconstruyen llamadas anteriores. El panel desglosa costes por usuario registrado, admin y visitante sin cuenta, y muestra la tendencia de las últimas ocho semanas. La migración `024` conserva el tipo de actor aunque se borre físicamente una cuenta; filas antiguas que ya no tenían `user_id` se clasifican como anónimas porque no se puede recuperar su origen. Los promedios semanales y acumulados suman el gasto atribuido a usuarios y admins y lo dividen entre las cuentas actuales con estado activo de ambos roles; por eso el gasto histórico de una cuenta eliminada puede seguir en el numerador sin estar en el denominador. El gasto anónimo sí se incluye en los totales, pero no en el promedio por cuenta. Los modelos sin tarifa configurada se señalan como eventos sin precio y no suman al importe estimado. Estas cifras no son contabilidad ni facturas reales. La bandeja de contacto ofrece respuesta por correo con destinatario consultado por el servidor; el cuerpo no se conserva. Si el resultado de SMTP es incierto, el panel exige revisar el buzón antes de autorizar un reintento. No hay lectura IMAP en la app.
El panel `AdminDashboard` organiza el resumen y los mensajes de contacto en `/panel-control`, y ofrece pestañas informativas de benchmark, telemetría de IA y seguridad. No ejecuta esas tareas desde el navegador. En la tabla de errores, solo aparecen incidencias HTTP 5xx agrupadas por código y diagnóstico seguro, con la última fecha y un enlace que abre el evento más reciente en una pestaña nueva. El detalle identifica el caso de uso, el estado HTTP y el diagnóstico. Los errores 5xx de `POST /api/evaluation-process` conservan el texto enviado, limitado a 2.000 caracteres, para que el equipo administrador pueda investigar el caso; la ruta requiere autenticación y rol admin y el dato se elimina con el evento a los 30 días. No se guardan texto de excepción ni respuestas crudas del proveedor. Otros errores no conservan payload de entrada. Las respuestas 4xx esperables no se cuentan. Para el detalle del contrato, los datos y sus límites de retención, consulta [`doc/admin-dashboard.md`](../doc/admin-dashboard.md) y [`persistence.md`](persistence.md).

Los usos de planes, ideas aprobadas, compras, contactos y contadores persistentes de roast se asocian al `userId` obtenido del token y no a la máquina o navegador. Cada perfil de navegador comparte una sola cookie de refresh entre sus pestañas: iniciar sesión con otra cuenta sustituye la sesión disponible para ese perfil y las pestañas abiertas reciben un aviso y se recargan para no conservar vistas locales de la cuenta anterior. No se ofrecen sesiones simultáneas de cuentas distintas en pestañas del mismo perfil; perfiles de navegador separados mantienen sus cookies independientes. La cuota gratuita de tres usos continúa siendo por perfil de navegador según `manageUserUnknow`; por ello, cuando una cuenta no tiene activo el plan del ámbito, comparte ese cupo de navegador con las demás cuentas usadas en ese navegador. Este cupo no concede rol admin ni plan, y las operaciones protegidas siguen autorizándose contra el usuario del token y el estado vigente en PostgreSQL.

Solo se agregan a PostgreSQL los errores de servidor HTTP 5xx, con código seguro, estado y fecha; algunos errores de evaluación incluyen una categoría cerrada y validada. Para los errores 5xx de `POST /api/evaluation-process`, `context_json` puede guardar hasta 2.000 caracteres del texto de idea para diagnóstico, accesible solo desde el detalle protegido para Jappy y eliminado con el evento a los 30 días. No se guardan rutas, cuerpos generales, mensajes de contacto, credenciales, mensajes de excepción ni respuestas crudas del proveedor. Las respuestas 4xx esperables (por ejemplo 401, 403, 404 o 429) no se cuentan como errores del panel. La bandeja muestra hasta 100 mensajes recientes con alias, correo, asunto, contenido, fecha y estado de correo; solo tiene acceso Jappy y el contenido no va a logs. Los mensajes se purgan a los 12 meses y las métricas agregadas a los 12 meses (errores, a los 30 días) mediante `DataRetentionService`; verificar ejecución en producción.
