# Componentes, carpetas y dependencias

## Regla de diseño

Aplicar AGENTS.md: las piezas usadas por una feature quedan locales; solo lo usado realmente por dos o más features pasa a shared. Los nombres describen funciones de negocio. Desarrollo Seguro usa el mismo monorepo, build y release, pero mantiene fronteras claras para poder extraerse después.

## Estado de implementación local

La fase técnica 1 y el endurecimiento local de ingesta hasta migration 005 están completados y verificados: PostgreSQL aislado pasó 52/52, 0 omitidas, el 2 de noviembre de 2026. La migración local 006 añade `controls-v3`, conserva la cobertura exacta de v2 y requiere `finalScheme=https` antes de permitir `pass` para DS-HDR-01; el core y PostgreSQL comparten esa garantía. PostgreSQL aislado pasó 65/65 pruebas tras migration 006, 0 omitidas, el 3 de noviembre de 2026. `controls-v1` y `controls-v2` mantienen su contrato histórico. El worker valida hostname canónico antes de llamar al puerto executor y contiene un adaptador DNS aislado descrito abajo. El adaptador y el seam HEAD todavía no ejecutan solicitudes ni abren socket; siguen pendientes el pinning de extremo a extremo, firewall/egress y capacidad VPS. El executor/red está bloqueado hasta superar esos gates. Los paquetes locales actuales son `apps/prototype-desarrollo-seguro/prototype-desarrollo-seguro-core/`, `apps/prototype-desarrollo-seguro/prototype-desarrollo-seguro-persistence/`, `apps/prototype-desarrollo-seguro/prototype-desarrollo-seguro-api/` y `apps/prototype-desarrollo-seguro/prototype-desarrollo-seguro-worker/`; siguen separados de los módulos de negocio de Grumphya.

El módulo `src/pinned-dns-lookup.ts` del worker exporta `createPinnedLookup`, un adaptador aislado del tipo `LookupFunction` de Node. Normaliza el hostname y llama al resolver en cada invocación; comprueba **todas** las respuestas A/AAAA recibidas antes de filtrar por la familia solicitada. Rechaza el conjunto completo si está vacío, excede el límite o contiene una dirección que incumple la política local de IP global; deduplica respuestas equivalentes y transforma errores del resolver/validación en fallo cerrado. El consumidor tiene un deadline probado de cinco segundos, pero esto no cancela `dns.lookup`/`getaddrinfo`. El singleton de esta instancia del módulo admite hasta dos resoluciones DNS concurrentes entre las instancias del adaptador que usan el limitador por defecto, y conserva cada plaza hasta que el resolver real termina, incluso si el consumidor ya recibió timeout. Este límite no cubre llamadas DNS ajenas al adaptador ni otras copias del módulo (por ejemplo, en otro worker thread). Como el resolver predeterminado usa `dns.lookup`/libuv, antes de integrar hay que reservar capacidad del threadpool o usar un resolver dedicado, además de establecer límites globales de tasa/concurrencia. La política de rangos debe mantenerse frente a los registros de [IANA IPv4 Special-Purpose](https://www.iana.org/assignments/iana-ipv4-special-registry) y [IANA IPv6 Special-Purpose](https://www.iana.org/assignments/iana-ipv6-special-registry). Este adaptador no está conectado a un executor ni a un cliente HTTP, no demuestra que la conexión use la dirección devuelta y no valida TLS, redirecciones, reintentos ni firewall. No equivale a un escáner seguro ni habilita scans.

`src/pinned-https-head-request.ts` exporta `createPinnedHttpsHeadRequest`, que valida el hostname y llama a `https.request` con método HEAD, ruta `/`, HTTPS/443, `Host` y SNI iguales al hostname normalizado, `lookup` pinned y `agent: false`. Solo construye y devuelve el `ClientRequest`: no llama a `.end()`, por lo que no abre socket ni envía tráfico. Sus pruebas capturan las opciones con un `requestFactory` falso; no hacen DNS ni tráfico de red. Este seam no es un executor ni implementa redirecciones. Tampoco implementa timeouts de conexión/TLS/headers/respuesta, cancelación, límites de bytes ni lectura/gestión de la respuesta; el timeout DNS no limita el tiempo de socket. No prueba qué IP usaría el socket, certificado TLS real ni firewall/egress. No integrarlo como executor hasta que el caller aplique esos límites y revalide hostname/DNS en cada conexión y salto; no habilita scans.

El bootstrap standalone de la API escucha en `0.0.0.0:3001` (configurable con `DS_API_PORT`). Las rutas de estado e informe solo leen snapshots e informes existentes: sin datos el estado es `not_scanned`; no resuelven dominios, encolan ni inician escaneos. La respuesta no contiene `evidence_json` crudo y ambas rutas envían `Cache-Control: no-store`. El limitador local aplica ventanas fijas de 60 segundos: 60 solicitudes por IP efectiva para cada GET, 120 por hostname para `status`, 120 por UUID válido para `reports` y 300 globales. Usa memoria de proceso, se reinicia con la API y no se comparte entre instancias. `DS_TRUSTED_PROXY_CIDRS` está vacío por defecto y rechaza wildcard `/0`; al integrarla detrás de Caddy, confiar solo en la IP/subred interna mínima del proxy. Antes de exposición pública hay que validar umbrales y, si se escala a varias instancias, usar un store compartido. No está conectada a Compose ni publicada en producción; al integrarla, debe quedar solo en una red interna, accesible desde Caddy y sin puerto de host. No hay UI de consulta desplegada. La decisión de ubicar los paquetes bajo `apps/` sigue la estructura actual del workspace; se mantienen dentro del módulo DS y no como utilidades globales de Grumphya.

El `pnpm-workspace.yaml` incluye los patrones `apps/*` y `apps/prototype-desarrollo-seguro/*`; el segundo descubre esos cuatro paquetes dentro del workspace anidado. La carpeta contenedora organiza la feature DS y el prefijo `prototype-` de los nombres de paquete no significa que sean parte del sitio estático actual ni que exista un escáner operativo. No se añadió una raíz `packages/*`: los paquetes siguen dentro del módulo de Desarrollo Seguro, no como utilidades globales de Grumphya. No crear paquetes compartidos para consumidores hipotéticos fuera de esta feature. La API y el processor de worker comparten contratos inmutables y persistencia propia, no objetos mutables en memoria. El probe y el conector de salida siguen pendientes y deberán formar la frontera de red del [modelo de amenazas](scanner-safety.md); su implementación depende de firewall/egress probado y de capacidad suficiente del VPS, y pueden empaquetarse en imágenes separadas dentro del mismo Compose y release.

## Encaje con rutas y código existentes

- Caddy recibe /api/desarrollo-seguro/* antes del manejador general /api/* y lo envía a la API nueva mediante HTTPS interno verificado. El resto de /api/* sigue en Nest Grumphya.
- Nginx conserva /desarrollo-seguro/ como landing de `prototype-desarrollo-seguro/`. Una regla más específica sirve /desarrollo-seguro/app/* desde el build React nuevo, con fallback solo a su index. El resto de la SPA Grumphya no cambia.
- El footer de Grumphya cambia únicamente el href y el texto/imagen neutral del sello local. No importa el cliente del escáner ni realiza solicitudes a un nuevo origen.
- La antigua ficha /acreditaciones/DS-GRUMPHYA-2026-001 y GET /api/accreditations/:id siguen disponibles como demostración histórica y enlazan al informe operativo; no se usan como fuente de los resultados nuevos.
- Las fechas manuales del registro antiguo no se copian a scan_runs.

## Dependencias permitidas

La web Desarrollo Seguro llama solo a su API bajo el mismo origen. La API nueva depende de su núcleo y su repositorio PostgreSQL. El worker depende del núcleo, cola/almacenamiento propio y conector de red protegido. Grumphya no depende de la API nueva para servir su funcionalidad central. La base Desarrollo Seguro no tiene FK a usuarios, ideas, planes, sesiones o avatares. No usar claves de OpenAI o correo de Grumphya.

Un fallo del worker deja resultados stale y alerta, pero no debe provocar reinicios del proxy, Grumphya API ni PostgreSQL. El paso futuro a otro dominio sustituye rutas/proxy y mueve esta unidad de código y datos, sin reescribir las reglas.
