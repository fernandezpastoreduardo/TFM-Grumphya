# Componentes, carpetas y dependencias

## Regla de diseño

Aplicar AGENTS.md: las piezas usadas por una feature quedan locales; solo lo usado realmente por dos o más features pasa a shared. Los nombres describen funciones de negocio. Desarrollo Seguro usa el mismo monorepo, build y release, pero mantiene fronteras claras para poder extraerse después.

## Estado de implementación local

La fase técnica 1 y el endurecimiento local de ingesta hasta migration 005 están completados y verificados: PostgreSQL aislado pasó 52/52, 0 omitidas, el 2 de noviembre de 2026. La migración local 006 añade `controls-v3`, conserva la cobertura exacta de v2 y requiere `finalScheme=https` antes de permitir `pass` para DS-HDR-01; el core y PostgreSQL comparten esa garantía. PostgreSQL aislado pasó 65/65 pruebas tras migration 006, 0 omitidas, el 3 de noviembre de 2026. `controls-v1` y `controls-v2` mantienen su contrato histórico. La suite API pasó 68/68 en una revisión anterior. El worker valida hostname canónico y contiene adaptadores DNS y transporte HTTPS probados con una fixture TLS local; en esta fase local, los tests del worker pasaron 95/95, además de typecheck y lint. El transporte ya abre sockets HTTPS reales dentro de pruebas locales: fija hostname/Host/SNI y puerto 443, vuelve a resolver mediante el lookup pinned en cada salto, exige TLS verificado, limita método/ruta/redirecciones/tiempo/tamaño, permite cancelar y no conserva el cuerpo. Esto prueba la lógica del cliente frente a un servidor de loopback, no la política del VPS. No está conectado al processor, a un worker arrancable ni a una API de ejecución; siguen bloqueados el egress IPv4/IPv6 efectivo, el conector por hostname, las pruebas adversarias de red desde cada rol y la capacidad del VPS bajo carga. Los paquetes DS siguen separados de los módulos de negocio de Grumphya.

El módulo `src/pinned-dns-lookup.ts` del worker exporta `createPinnedLookup`, un adaptador aislado del tipo `LookupFunction` de Node. Normaliza el hostname y llama al resolver en cada invocación; comprueba **todas** las respuestas A/AAAA recibidas antes de filtrar por la familia solicitada. Rechaza el conjunto completo si está vacío, excede el límite o contiene una dirección que incumple la política local de IP global; deduplica respuestas equivalentes y transforma errores del resolver/validación en fallo cerrado. El consumidor tiene un deadline probado de cinco segundos, pero esto no cancela `dns.lookup`/`getaddrinfo`. El singleton de esta instancia del módulo admite hasta dos resoluciones DNS concurrentes entre las instancias del adaptador que usan el limitador por defecto, y conserva cada plaza hasta que el resolver real termina, incluso si el consumidor ya recibió timeout. Este límite no cubre llamadas DNS ajenas al adaptador ni otras copias del módulo (por ejemplo, en otro worker thread). Como el resolver predeterminado usa `dns.lookup`/libuv, antes de ejecutarlo en producción hay que reservar capacidad del threadpool o usar un resolver dedicado, además de establecer límites globales de tasa/concurrencia. La política de rangos debe mantenerse frente a los registros de [IANA IPv4 Special-Purpose](https://www.iana.org/assignments/iana-ipv4-special-registry) y [IANA IPv6 Special-Purpose](https://www.iana.org/assignments/iana-ipv6-special-registry). Integrado en `pinned-https-transport.ts`, Node entrega este lookup al cliente por conexión y redirección; esa integración sí se ha probado con un lookup de loopback controlado. El adaptador, por sí solo, no demuestra una barrera de red del VPS, aislamiento del executor ni autorización por hostname del conector. No equivale a un escáner operativo ni habilita scans.

`src/pinned-https-transport.ts` exporta `requestPinnedHttps`, el transporte HTTPS local de bajo nivel. Valida método y ruta declarada, usa TLS con verificación de certificado y hostname, `Host`/SNI y puerto 443 fijos, `agent: false`, y `createPinnedLookup` en cada conexión/redirección. Solo sigue hasta tres redirecciones HTTPS al mismo hostname y a una ruta exacta del scope, limita cada solicitud con deadline total de 10 s, aborta mediante `AbortSignal`, drena la respuesta sin retener su cuerpo y corta al superar 64 KiB. Devuelve estado, ruta final, IP observada y resultado de autorización TLS. La suite abre un servidor TLS de loopback con CA de test y verifica pinning de socket, SNI/Host, verificación TLS, redirecciones y rechazos; usa seams inyectables solo para CA, puerto de fixture y lookup loopback. La clave/certificado fixture no son credenciales de producción.

Este transporte todavía no es un executor operativo: el processor se ejercita con él únicamente en un test de fixture/store simulado; no hay wiring productivo con los jobs, API ni proceso worker arrancable y tampoco interpreta los controles para construir evidencia completa. Los tests no verifican firewall, rutas Docker, aislamiento de roles, DNS/IP desde el VPS ni destinos públicos. Antes de conectarlo al worker ejecutable hacen falta un conector de salida no genérico con allowlist por hostname, política efectiva de firewall `INPUT`/`FORWARD` para IPv4 e IPv6, pruebas desde namespaces/roles aislados y medición bajo carga; los gates se mantienen en [operations.md](operations.md#diseño-de-aislamiento-de-salida-pendiente-de-implementar). No habilita scans.

El bootstrap standalone de la API escucha en `0.0.0.0:3001` (configurable con `DS_API_PORT`). Las rutas de estado e informe solo leen snapshots e informes existentes: sin datos el estado es `not_scanned`; no resuelven dominios, encolan ni inician escaneos. La respuesta no contiene `evidence_json` crudo y ambas rutas envían `Cache-Control: no-store`. El portal React consulta esas rutas: al enviar el formulario solicita `status` y `?report=<uuid>` carga un informe por ID. En desarrollo, Vite tiene proxy DS específico; la configuración general `/api/*` sigue enrutando a Grumphya. Para producción ya existe un Compose/Caddy alternativo opt-in: la API se coloca en redes internas sin puerto de host y Caddy enruta `/api/desarrollo-seguro/v1/*` al upstream TLS DS antes de la ruta genérica. El input `enable_development_security` del workflow manual de `main` está apagado por defecto; el portal y servicios no se han desplegado ni activado en VPS. No se usan datos simulados ni se inician otras operaciones. El limitador local aplica ventanas fijas de 60 segundos: 60 solicitudes por IP efectiva para cada GET, 120 por hostname para `status`, 120 por UUID válido para `reports` y 300 globales. Usa memoria de proceso, se reinicia con la API y no se comparte entre instancias. `DS_TRUSTED_PROXY_CIDRS` está vacío por defecto en API standalone y rechaza wildcard `/0`; el overlay lo limita a la IP interna de Caddy. Antes de exposición pública hay que validar umbrales y, si se escala a varias instancias, usar un store compartido. El overlay incluye API y PostgreSQL DS con bootstrap, pero no contiene worker, probe ni executor; no habilita escaneos. La CSP aplicada actualmente solo incluye `base-uri`, `object-src`, `frame-ancestors` y `form-action`; no define `default-src` ni `script-src`. La política más estricta sigue en `Content-Security-Policy-Report-Only`; antes de desplegar el portal hay que revisar los informes de sus recursos, sin asumir que la CSP aplicada restringe scripts. La decisión de ubicar los paquetes bajo `apps/` sigue la estructura actual del workspace; se mantienen dentro del módulo DS y no como utilidades globales de Grumphya.

El `pnpm-workspace.yaml` incluye los patrones `apps/*` y `apps/prototype-desarrollo-seguro/*`; el segundo descubre esos cinco paquetes dentro del workspace anidado. La carpeta contenedora organiza la feature DS y el prefijo `prototype-` de los nombres de paquete no implica que exista un escáner operativo. No se añadió una raíz `packages/*`: los paquetes siguen dentro del módulo de Desarrollo Seguro, no como utilidades globales de Grumphya. No crear paquetes compartidos para consumidores hipotéticos fuera de esta feature. La API y el processor de worker comparten contratos inmutables y persistencia propia, no objetos mutables en memoria. El portal es una vista local de solo lectura; el probe y el conector de salida siguen pendientes y deberán formar la frontera de red del [modelo de amenazas](scanner-safety.md); su implementación depende de firewall/egress probado y de capacidad suficiente del VPS, y pueden empaquetarse en imágenes separadas dentro del mismo Compose y release.

## Encaje con rutas y código existentes

- Caddy aún no enruta `/api/desarrollo-seguro/*`; el manejador general `/api/*` envía a Grumphya `api:3000`. Añadir una ruta específica anterior al manejador general y un servicio DS API en Compose, escuchando internamente en 3001 sin puerto host y accesible mediante HTTPS interno verificado. En desarrollo, configurar un proxy Vite específico para `/api/desarrollo-seguro/*` al DS API local en 3001 y conservar el proxy general a Grumphya para el resto de `/api/*`.
- Nginx conserva /desarrollo-seguro/ como landing de `prototype-desarrollo-seguro/`. La configuración local sirve `/desarrollo-seguro/app` desde el build React mediante una regla exacta; la integración de producción y sus rutas profundas siguen pendientes. El resto de la SPA Grumphya no cambia.
- El footer de Grumphya cambia únicamente el href y el texto/imagen neutral del sello local. No importa el cliente del escáner ni realiza solicitudes a un nuevo origen.
- La antigua ficha /acreditaciones/DS-GRUMPHYA-2026-001 y GET /api/accreditations/:id siguen disponibles como demostración histórica y enlazan al informe operativo; no se usan como fuente de los resultados nuevos.
- Las fechas manuales del registro antiguo no se copian a scan_runs.

## Dependencias permitidas

La web Desarrollo Seguro llama solo a su API bajo el mismo origen. La API nueva depende de su núcleo y su repositorio PostgreSQL. El worker depende del núcleo, cola/almacenamiento propio y conector de red protegido. Grumphya no depende de la API nueva para servir su funcionalidad central. La base Desarrollo Seguro no tiene FK a usuarios, ideas, planes, sesiones o avatares. No usar claves de OpenAI o correo de Grumphya.

Un fallo del worker deja resultados stale y alerta, pero no debe provocar reinicios del proxy, Grumphya API ni PostgreSQL. El paso futuro a otro dominio sustituye rutas/proxy y mueve esta unidad de código y datos, sin reescribir las reglas.
