# Orden de ejecución para Luna

## Mandato y condiciones

Implementar la **primera fase operativa dentro del despliegue actual de Grumphya**: mismo dominio grumphya.com, VPS, repositorio y release manual, con componentes DS aislados. El escaneo real de bajo impacto sigue bloqueado por sus gates. Seguir [README.md](README.md), el perfil [controls-and-evidence.md](controls-and-evidence.md), la seguridad [scanner-safety.md](scanner-safety.md), y el gate operativo [operations.md](operations.md). La fase técnica local está implementada. `controls-v1` conserva el perfil original de nueve controles; las migraciones `005_controls_v2_route_coverage.sql` y `006_controls_v3_https_headers.sql` y el core mantienen los perfiles aditivos `controls-v2`/`controls-v3` con cobertura exacta por ruta, y v3 exige `finalScheme=https` para que DS-HDR-01 pueda quedar en `pass`. La suite PostgreSQL aislada más reciente pasó 68/68, 0 omitidas, tras los cambios de grants de solo lectura, el 3 de noviembre de 2026; el limitador de lecturas tiene pruebas específicas para cuotas y `Retry-After`. La última validación local habilitada del paquete API pasó 93/93 el 3 de noviembre de 2026; los checks HTTP usan loopback y servicio stub local, sin base de datos ni red externa. En una ejecución previa dentro del sandbox, tres pruebas no pudieron enlazar localhost por `EPERM`; esa limitación del entorno quedó resuelta al ejecutar la suite en el entorno habilitado. Para este slice, los resultados focalizados y el estado de build/typecheck/lint están detallados en [operations.md](operations.md#verificación-local-de-proxy-y-tls-de-este-slice): el proxy Vite pasó 7/7 y las pruebas focalizadas del listener TLS 16/16. Hay un portal React local de solo lectura en `/desarrollo-seguro/app`, integrado en el router/build web y la ruta Nginx local: solo consulta status/report mediante GET y muestra el estado vacío/error si no hay informe o el API no responde. No crea ni encola trabajos ni inicia scans. La configuración Vite local ya enruta `/api/desarrollo-seguro` al target `DEVELOPMENT_SECURITY_API_PROXY_TARGET`, validado como HTTP loopback y con valor predeterminado `http://127.0.0.1:3001`; el proxy genérico `/api` de Grumphya conserva `API_PROXY_TARGET`.

La integración de lanzamiento DS quedó preparada como opt-in en `main`: el workflow manual `workflow_dispatch` tiene `enable_development_security`, que por defecto es `false`, además de la aprobación general de producción. Si el VPS conserva helper v2, primero debe recibir una release base con DS apagado para instalar v3; luego se podrá habilitar DS en otro workflow manual. Antes del one-shot de migración, el helper guarda el snapshot candidato y registra su SHA como pending; al completar la migración lo promueve a baseline y limpia pending antes de levantar el resto del stack. Si la finalización se interrumpe, pending y el snapshot se conservan y pasan a ser la referencia conservadora para siguientes intentos. Si un rollout falla, el retry del mismo SHA solo reutiliza ese baseline si las migraciones coinciden exactamente; un conflicto se rechaza. En upgrades y reactivaciones, helper v3 compara con el snapshot, exige que las migraciones aplicadas sigan byte por byte iguales y que cada archivo SQL nuevo incluya `-- deployment-rollback-compatible: true` y pase el bloqueo SQL destructivo. Solo `DROP TRIGGER IF EXISTS` se permite; no hay migración hacia abajo automática. El bundle incluye Compose alternativo e imágenes DS; el overlay añade PostgreSQL con volumen propio, bootstrap/migrador de una ejecución y API HTTPS, y configura Caddy para enrutar `/api/desarrollo-seguro/v1/*` por TLS upstream verificado. Requiere los secretos DS y certificados de API/DB indicados en [operations.md](operations.md#release-opt-in-de-desarrollo-seguro-desde-main). Esta preparación no se ha desplegado en VPS y no activa worker, probe, executor ni escaneos. Si fallan los health checks posteriores, el rollback retira contenedores DS y conserva volumen, esquema y snapshot; no ejecuta una migración hacia abajo. Los snapshots y los punteros baseline/pending quedan bajo `$ROOT/state` y sobreviven a releases base y pruning. Las migraciones futuras deben mantener compatibilidad con la release anterior y validarse antes de reactivar DS; backup/restore sigue pendiente.

La etapa de executor/red permanece bloqueada hasta cerrar DNS/IP pinning, firewall/egress y medición de capacidad real del VPS. El despliegue de servicios no habilita escaneos públicos; estos requieren superar sus gates y el flujo manual aprobado.

Antes de cada siguiente slice, revisar AGENTS.md y el estado real del repo, Compose, Caddy/Nginx y workflows; registrar discrepancias con el diseño. No asumir que el prototipo o datos académicos son resultados reales. Mantener el cambio concentrado en DS, rutas compartidas necesarias y sello local.

## Entregas en slices verticales

### 0. Contrato, seguridad y prueba de capacidad

- Mantener `controls-v1` como contrato histórico intacto y versionar cualquier cambio de cobertura o criterios. `controls-v2` conserva la regla HEAD 405/501 + redirección HTTPS confirmada + esquema final HTTPS => `unknown`; `controls-v3`, añadido por migration 006, hereda esa regla y la cobertura exacta por ruta, y exige además `finalScheme=https` para permitir `pass` en DS-HDR-01. El core y PostgreSQL validan el gate v3. El evaluador local `security-headers-v1` define señales de HSTS, nosniff, protección de marcos, Referrer-Policy y CSP, pero la recolección desde una respuesta real sigue pendiente del executor. Cualquier otro cambio de criterios requiere una versión de perfil propia. Antes del executor, cerrar las rúbricas que siguen pendientes y resolver cualquier control que no pueda medirse con fiabilidad como unknown o advisory; no aprobarlo por defecto.
- El worker contiene un adaptador DNS aislado compatible con `LookupFunction`, con deadline de cinco segundos y un límite de dos resoluciones simultáneas para instancias por defecto que comparten esta instancia del módulo. No limita llamadas DNS ajenas al adaptador ni otras copias del módulo. El timeout no cancela `dns.lookup`/`getaddrinfo`, y la plaza permanece ocupada hasta que termine la resolución subyacente. Antes de integrarlo a HTTP/executor, reservar capacidad del threadpool de libuv o usar un resolver dedicado, y fijar límites globales de tasa/concurrencia del proceso. Documentar su integración en la arquitectura de probe/conector, el bloqueo de red aunque falle la validación de aplicación, rutas de grumphya.com y presupuesto de escaneo. El adaptador no implementa la frontera completa. Revisar viabilidad de IP pública desde el mismo VPS.
- El seam local `createPinnedHttpsHeadRequest` prepara `HEAD /` a HTTPS/443 con hostname normalizado en `Host`/SNI, `lookup` pinned y `agent: false`; no llama a `.end()` y no abre socket. Las pruebas usan un `requestFactory` falso y no hacen DNS ni tráfico. No es un executor, no sigue redirecciones y no demuestra selección de IP por el socket, TLS/certificado real ni firewall. Antes de cualquier executor siguen pendientes integración y pruebas de esas fronteras; no habilita scans.
- La auditoría read-only del firewall Linux/Docker local del 2 de noviembre y las lecturas por SSH del VPS del 3 de noviembre de 2026 no demuestran una barrera de egress efectiva. En esa captura, `DOCKER-USER` no tenía reglas y la red `grumphya_egress` informaba `internal=false` (`ipv6=false` solo para esa red); la tabla NAT mostraba publicaciones TCP 80/443 y UDP 443 hacia el contenedor de borde. `net.ipv6.conf.all.forwarding` se leyó como `0`, lo que no demuestra por sí solo el bloqueo completo de IPv6. No se probó conectividad ni se cambió configuración. IONOS VPS documenta un filtro externo centrado en tráfico entrante, que no sustituye el filtro de salida dedicado. Mantener el gate de firewall/egress bloqueado hasta implementar y verificar una política acotada a la subred DS para IPv4 e IPv6; el diagnóstico y el diseño están en [operations.md](operations.md#auditoría-de-egress-del-vps-solo-lectura-2-de-noviembre-de-2026) y [la revisión IONOS](operations.md#revisión-ionos-y-línea-base-del-vps-3-de-noviembre-de-2026).
- Levantar una línea base de capacidad del VPS y definir límites y umbrales en el PR. Si el hardware impide una sonda segura dentro de los límites, parar la publicación operativa y comunicar la causa.
- Escribir tests de amenaza y veredicto que fallen antes de implementar.

**Salida:** contratos y umbrales aprobables, fixtures de red, plan de observabilidad y evidencia de que el aislamiento es realizable.

### 1. Núcleo y persistencia DS

- Crear los componentes y paquetes DS sin imports de negocio Grumphya. Configurar build del monorepo y pruebas propias.
- Aprovisionar base lógica y roles DS de forma idempotente en entorno de prueba, migraciones propias, tablas de dominios, jobs, runs y controles. Separar roles de lectura/ejecución/migración.
- Implementar máquina de estados, cálculo de TTL exacto desde completed_at, historial inmutable, perfil versionado, lease, recuperación y singleflight.
- Tests TDD para frescura, concurrencia, reintentos, aislamiento de roles e invariantes de veredicto.

**Estado:** fase técnica 1 completada en local: paquetes, esquema y almacén PostgreSQL, contratos/pruebas, health API, endpoints GET de estado/informe y processor. No se ha provisionado ni migrado PostgreSQL de producción.

**CI PostgreSQL DS:** el workflow `.github/workflows/ci.yml` ejecuta `test:postgres` contra un servicio efímero independiente `pgvector/pgvector:0.8.7-pg17`, con bind `127.0.0.1:5433:5432`, base administrativa `development_security_test_admin` y credenciales sintéticas del job. La suite provisiona una base objetivo y roles DS y verifica permisos, migraciones, funciones SQL y comportamiento del almacén. El job de supply-chain también ejecuta un smoke de la imagen de producción con PostgreSQL temporal, TLS obligatorio y red interna sin salida; no activa servicios ni rutas del despliegue. El workflow incluye una ruta de release DS opcional desde `main`, pero no se ha ejecutado desde esta máquina; queda pendiente observar el run de CI y cualquier despliegue real. Las pruebas no validan VPS/producción, firewall/egress efectivo, carga, scans, rollback ni certificados de VPS. Véanse [suite PostgreSQL](operations.md#suite-de-integración-postgresql-ds-en-ci) y [smoke de imagen](operations.md#smoke-de-la-imagen-de-producción-ds-en-ci).

**Límites:** además de health, la API local expone solo lecturas de estado e informes. El portal local en `/desarrollo-seguro/app` consume esos GET si el API está disponible; no envía solicitudes de escritura. No admite ni crea jobs, no inicia scans; no hay UI desplegada, proceso worker arrancable ni executor real. El puerto de executor no convierte los jobs en escaneos.

### 2. Guardas de ingesta completadas; executor/red bloqueado

- El endurecimiento local de ingesta implementa allowlists, summaries/limitaciones fijos, evidencia mínima y derivación de estado entre TypeScript y SQL. `controls-v1` conserva los nueve IDs y su contrato original. `controls-v2` se añadió mediante `005_controls_v2_route_coverage.sql` sin recalificar v1 ni reutilizar su caché: exige DNS-01 + TLS-01 + TLS-02 una vez por host y, por cada ruta declarada, HTTP-01 HEAD/GET, HDR-01 GET, PRIV-01/02/03 GET y QUAL-01 GET. `controls-v3`, añadido por `006_controls_v3_https_headers.sql`, mantiene esa cobertura y exige `finalScheme=https` antes de permitir `pass` en DS-HDR-01. Total: 10, 17 o 24 checks para una, dos o tres rutas. La cobertura exacta y el guard de esquema se validan en core y PostgreSQL. La suite PostgreSQL aislada más reciente pasó 68/68, 0 omitidas, tras los cambios de grants de solo lectura, el 3 de noviembre de 2026.
- Para `grumphya.com`, el scope admitido queda limitado a `/`, `/precios` y `/acreditaciones/DS-GRUMPHYA-2026-001`; para otros dominios solo `/`. La política tipada por control está descrita en [controls-and-evidence.md](controls-and-evidence.md).
- En v2 y v3, un `HEAD` 405/501 con redirección HTTPS confirmada y esquema final HTTPS se normaliza a `unknown`; no puede sostener un `pass`. V3 no modifica el comportamiento histórico de v1/v2; requiere HTTPS explícito para aprobar DS-HDR-01. El evaluador `security-headers-v1` está descrito en [controls-and-evidence.md](controls-and-evidence.md); la extracción de señales desde respuestas reales no está conectada al executor. El worker incluye `createPinnedLookup`, que normaliza hostname y vuelve a resolver/valida todas las respuestas A/AAAA en cada invocación; el adaptador no se conecta al puerto executor, así que el pinning de la conexión y la revalidación en cada conexión/redirección siguen pendientes. El firewall/egress y capacidad también están pendientes.
- Estas guardas locales no conectan a ningún dominio ni equivalen a protección SSRF completa. La ejecución de red solo puede avanzar tras definir las rúbricas pendientes, añadir DNS/IP pinning y revalidación por conexión/redirección, disponer y probar firewall/egress que bloquee redes internas y terceros, y medir que el VPS soporta los límites del probe sin degradar Grumphya.

- Implementar admisión de hostname, DNS/TLS/HTTP, comprobación de cabeceras y navegador limpio por fases, con presupuesto global y firewall/proxy de salida. Se registran y bloquean intentos de terceros. Aplicar robots a rutas muestreadas.
- Probar cada control contra fixtures pass/fail/unknown y pruebas adversarias de SSRF reales. Registrar rutas, hora, método, versión y evidencia redactada.
- Ejecutar un escaneo controlado de grumphya.com desde el VPS solo tras validar límites; comprobar la perspectiva pública real. Repetir hasta obtener resultados estables, sin forzar un aprobado.

**Salida:** informe íntegro y trazable, con exactitud de fuente same_vps y cobertura.

### 3. API pública, portal y sello

- Implementar contratos de [DTOs.md](DTOs.md), búsqueda de dominio público acotada, cuotas, 200 de caché y 202 de trabajo único, polling y errores.
- Los GET locales de estado/informe ya aplican ventana fija: 60/minuto por IP efectiva, 120/minuto por hostname para `status`, 120/minuto por UUID válido para `reports`, 300/minuto global y `429` con `Retry-After`. Antes de exposición real, validar umbrales y configurar `DS_TRUSTED_PROXY_CIDRS` solo para la IP/subred interna mínima del proxy; vacío por defecto y rechazo de wildcard `/0`. Si se despliega más de una instancia, usar almacenamiento compartido; el limitador en memoria es por proceso.
- Ampliar el portal React local existente en `/desarrollo-seguro/app/` y conservar la landing. La versión actual solo permite consultar estado e informe mediante GET; la búsqueda operativa, historial, antigüedad, alcance, límites, resultados unknown y estados no vigentes requieren el API de scans y sus gates. Mantener accesibilidad y recursos locales.
- El proxy Vite específico para `/api/desarrollo-seguro` ya está implementado para desarrollo local: `DEVELOPMENT_SECURITY_API_PROXY_TARGET` usa `http://127.0.0.1:3001` por defecto y rechaza destinos que no sean HTTP loopback o incluyan credenciales; el proxy `/api` general de Grumphya se conserva. Para el lanzamiento de producción existe un Compose alternativo opt-in con API DS interna sin puerto de host y Caddy enruta `/api/desarrollo-seguro/v1/*` antes del proxy general, con HTTPS interno verificado y `DS_TRUSTED_PROXY_CIDRS` acotado a la IP interna de Caddy. Esta variante está empaquetable desde `main`, desactivada por defecto, y no ha sido desplegada; requiere el conjunto de secretos/certificados DS y validación operativa descritos en [operations.md](operations.md#release-opt-in-de-desarrollo-seguro-desde-main). Hasta arrancar el API DS, la consulta del portal muestra error.
- Revisar informes `Report-Only` del bundle del portal antes de desplegar. La CSP aplicada no incluye `default-src` ni `script-src`; no describirla como restricción de scripts ni ampliarla sin evidencia y revisión según [doc/production.md](../../doc/production.md).
- En el footer, cambiar texto/arte neutral a un enlace local al informe operativo; no insertar scripts ni recursos terceros. Mantener la ficha /acreditaciones/ histórica como demostración y enlazar desde ella al informe.
- Tests de UI/E2E y privacidad para entrada por búsqueda y por sello.

**Salida:** ambos caminos generan la misma consulta, sin confundir datos del TFM con evidencia operativa.

### 4. Horario, despliegue y activación gradual

- Activar scheduler solo para grumphya.com verificado, con intervalo de 60 minutos, idempotencia, cuotas y prioridad limitada. Monitorear stale/errores, leases, carga y almacenamiento.
- La variante opt-in de Compose/Caddy y la ruta workflow desde `main` ya están preparadas. El `Dockerfile` contiene el target `development-security-production`, que fija `DS_API_TLS_REQUIRED=true`; el smoke de imagen pasó en Docker Desktop con PostgreSQL y TLS aislados. El flujo alternativo incluye un contenedor PostgreSQL DS y un bootstrap/migrador de una sola ejecución, API HTTPS y Caddy con upstream autenticado por CA interna. El input `enable_development_security` sigue apagado por defecto; su activación requiere además el flujo manual aprobado de producción. No se ha realizado un despliegue real ni se ha observado todavía un run del workflow desde esta máquina. Antes de usarlo faltan provisioning de secretos/certificados en el VPS, revisión final de topología/red, backups/restore y aceptación de health/rollback. El rollback conserva el volumen DS nombrado, pero no se ha probado sobre una base real.
- Observar el run pendiente de CI, completar pruebas de carga y seguridad, varios ciclos horarios reales y revisión humana de falsos positivos y textos. La aprobación de despliegue sigue el workflow_dispatch vigente; no activar la búsqueda pública antes de superar las puertas.
- Si una puerta falla, dejar el estado como no evaluable/caducado y resolver el problema. No reducir silenciosamente el perfil para conseguir un sello.

**Salida:** fase operativa verificable sin dominio ni hosting nuevo, con Grumphya estable y un procedimiento de reversión probado.

## Criterio final de aceptación

Se puede mostrar «cumple controles observables v1» **solo** con escaneo completo de menos de 60 minutos, perfil vigente, muestra declarada y todos los obligatorios evaluables aprobados. Fallo, unknown, error de red o vencimiento no dan aprobado. El informe debe revelar la fuente same_vps. El siguiente proyecto independiente se planifica cuando exista dominio y una decisión de migración; no forma parte de esta entrega.
