## Estado actual

Los paquetes DS de API, persistencia y worker existen en el workspace. La migración 003 protege claim/renew/recover/complete mediante funciones `SECURITY DEFINER`; el worker no tiene escritura directa de jobs ni informes. `controls-v1` conserva sus nueve controles y contrato; `controls-v2` añade cobertura exacta en migration 005, y migration 006 añade `controls-v3` con la misma cobertura y exige `finalScheme=https` para aprobar DS-HDR-01. Core y SQL aplican esa condición; v1/v2 mantienen sus criterios históricos. PostgreSQL aislado pasó 65/65 pruebas tras migration 006, 0 omitidas, el 3 de noviembre de 2026. La cobertura solo abarca las rutas declaradas: scope `/` cubre únicamente portada y no implica aprobación de las demás superficies. El informe debe exponer las rutas medidas. Estas garantías locales validan forma, cobertura y coherencia semántica del payload, pero no prueban que un worker comprometido no fabrique evidencia permitida; la autenticidad y recolección de evidencia serán responsabilidad de la futura frontera confiable del executor.

El worker rechaza hostname inválido/no canónico antes de llamar al puerto executor, contiene un adaptador `LookupFunction` aislado que valida todas las respuestas DNS A/AAAA por llamada y un seam que prepara una petición HTTPS HEAD pinned sin enviarla ni abrir socket. Las pruebas del seam usan un `requestFactory` falso y no generan DNS ni tráfico. No hay executor de red: no se ha probado el socket/IP, TLS/certificado real ni firewall/egress; tampoco hay gestión de redirecciones o límites HTTP de conexión, respuesta, cancelación y bytes. En `controls-v2` y `controls-v3`, un `HEAD` 405/501 tras redirección HTTPS confirmada y esquema final HTTPS se normaliza a `unknown`. Estas garantías siguen siendo locales y requieren revisión de grants en el gate previo a producción.

La API local expone health y dos lecturas `GET` de estado/informe con `Cache-Control: no-store`; no crea jobs ni inicia scans, y no devuelve `evidence_json` crudo. Si no hay informe devuelve `not_scanned`; la exclusión de un dominio también oculta sus informes por ID. El portal React local en `/desarrollo-seguro/app` consulta únicamente esos GET: el formulario solicita status y `?report=<uuid>` carga un informe existente. La configuración de desarrollo Vite ya enruta `/api/desarrollo-seguro` a `DEVELOPMENT_SECURITY_API_PROXY_TARGET` (por defecto `http://127.0.0.1:3001`); valida que el destino sea HTTP loopback (`localhost`, `127.0.0.1` o `[::1]`) y no incluya credenciales. El proxy genérico `/api` conserva `API_PROXY_TARGET` (por defecto `http://127.0.0.1:3000`) para Grumphya. En desarrollo, el API acepta `DS_DATABASE_URL` o lee la URL desde `DS_DATABASE_URL_FILE`; debe haber exactamente una fuente no vacía. La lectura desde archivo también es obligatoria si `NODE_ENV=production` o `DS_DATABASE_URL_FILE_REQUIRED=true`. Este flag solo acepta los valores exactos `true` y `false`; con `true` exige el archivo incluso si se cambia `NODE_ENV`. El archivo se lee como UTF-8 y se elimina un único salto de línea final LF o CRLF. La URL debe usar `postgres:` o `postgresql:`, incluir host, base de datos, usuario y contraseña, no tener espacios exteriores ni saltos de línea restantes, y no incluir query ni fragment. Cuando se requiere el archivo, además exige el usuario `ds_api` y la base `desarrollo_seguro`, evitando que una configuración de producción apunte a la base de Grumphya. Si hay fuentes ambiguas, el archivo no se puede leer o la URL no es válida, falla con un error genérico que no incluye la ruta ni el secreto. Esta preparación todavía no está conectada a un secreto de Compose. Caddy sigue enviando `/api/*` al API de Grumphya; no hay ruta Caddy específica ni servicio DS en Compose, por lo que el API DS no es accesible desde el dominio ni está desplegado.

El limitador en proceso aplica ventanas fijas de 60 segundos: 60 solicitudes/minuto por IP efectiva para ambos GET, 120/minuto por hostname solo para `status`, 120/minuto por UUID válido para `reports` y 300/minuto global; al excederlas responde 429 con `Retry-After`. Su almacenamiento en memoria se reinicia al reiniciar el servicio y no se comparte entre instancias. `DS_TRUSTED_PROXY_CIDRS` está vacío por defecto y rechaza wildcard `/0`; al integrar detrás de Caddy, configurar solo la IP/subred interna mínima del proxy. Los límites y el proxy confiable requieren validación antes de exposición real; varias instancias requieren un store compartido.

En desarrollo local el listener puede usar HTTP, salvo que se active TLS. Con `NODE_ENV=production`, TLS es obligatorio independientemente de `DS_API_TLS_REQUIRED`; este parámetro, si está presente, solo acepta los valores exactos `true` o `false`, y `true` obliga a TLS también fuera de producción. El API requiere `DS_API_TLS_CERT_FILE` y `DS_API_TLS_KEY_FILE`, fija TLS 1.2 como mínimo y admite TLS 1.3. `DS_API_TLS_CLIENT_CA_FILE` es opcional; si se configura, cada certificado PEM del bundle debe parsear como X509 y marcar `CA:TRUE`, y el listener exige certificado de cliente verificado. La API tampoco está aprovisionada contra la base productiva: el provisionador/migraciones DS siguen siendo código local y requieren un flujo separado y controlado. La configuración del pool PostgreSQL lee `DS_DATABASE_TLS_CA_FILE`; `NODE_ENV=production` o `DS_DATABASE_TLS_REQUIRED=true` hacen obligatoria la CA, y el flag solo acepta los valores exactos `true`/`false` (producción fuerza TLS aunque se cambie el flag). El bundle debe contener uno o más certificados X509 PEM con `CA:TRUE` y sin contenido extra; las opciones de `pg` reciben `ca` y `rejectUnauthorized: true`, por lo que TLS valida la cadena y el nombre del servidor según el hostname de la URL. Los errores de lectura o validación son genéricos. Aún no se puede conectar desde Compose/Caddy ni en el VPS: faltan la base DS y el rol `ds_api` aprovisionados, el secreto de URL, y el certificado/CA TLS del servidor PostgreSQL.

### Diseño de aislamiento de salida pendiente de implementar

El servicio de Desarrollo Seguro no debe compartir la red `egress` de Grumphya. La topología propuesta separa:

- API y worker en la red interna de datos DS, sin ruta directa a Internet.
- Probe en una red Docker `internal: true`, sin credenciales, secretos, Docker socket ni montajes del host.
- Un único conector sin acceso a PostgreSQL, alcanzable por el probe solo en la red interna, como único componente con una interfaz de salida.
- Una cadena de firewall del host aplicada mediante `DOCKER-USER` (IPv4 e IPv6) que permite DNS solo a resolvers explícitos por UDP/TCP 53, limita el egress del conector a destinos aprobados y bloquea redes locales, Docker, RFC1918, loopback, link-local, metadatos y rangos especiales. El resto del tráfico desde la subred dedicada se deniega. Si la política solo puede limitar a cualquier IP pública en TCP 80/443, no impide el abuso contra terceros desde un conector comprometido y no satisface este gate: se requiere un proxy de salida con política por hostname o mantener bloqueado el executor. No se cambian las reglas generales ni las redes de Grumphya.
- `DOCKER-USER` cubre tráfico reenviado (`FORWARD`), no tráfico del contenedor dirigido a una IP/interfaz local del host, que atraviesa `INPUT`. La política debe denegar también el acceso al host desde las interfaces/subredes DS, con excepciones mínimas justificadas. Probar desde conector, probe y worker el acceso a la gateway del bridge y a servicios del host, además del acceso a otros contenedores/redes; el conector no debe servir como ruta indirecta a esos destinos.
- El conector resuelve y valida cada A/AAAA y fija la dirección validada en el socket en cada conexión/redirección; valida el hostname permitido antes de abrir la conexión, y no ofrece un proxy genérico ni `CONNECT` arbitrario. El firewall IP es defensa adicional: por sí solo no distingue dominios públicos y no sustituye la política por hostname.
- La red `internal: true` y la conexión dual-homed del conector no son controles de egress suficientes por sí mismos. Se debe probar que probe/worker no pueden reenviar o enrutar tráfico directamente y que solo alcanzan la interfaz/protocolo mínimo del conector. IPv6 debe quedar bloqueado/deshabilitado de forma efectiva tanto en Docker como en el host hasta validar la política completa; la falta de ruta IPv6 observada en una captura no sirve como control.

La subred dedicada, los resolvers permitidos y las reglas exactas deben fijarse junto con el Compose del probe/conector, después de comprobar que no colisionan con redes del VPS. Las reglas en `DOCKER-USER` deben diseñarse considerando que el tráfico reenviado normalmente ya pasó por DNAT; validar `conntrack --ctorigdst`/`--ctorigdstport` cuando corresponda y probar el flujo efectivo, incluido el hairpin al IP público de Grumphya. Bloquear destinos de redes Docker puede romper ese hairpin; permitir el IP público puede llegar a cualquier vhost/ruta de Caddy, así que el dominio propio requiere una decisión explícita de topología y política, no solo una excepción por IP. Añadir y probar reglas `INPUT` para denegar desde interfaces/subredes DS el acceso directo a la gateway y servicios del host: ese tráfico no pasa por `DOCKER-USER`. Antes de aplicar reglas persistentes se necesita un script idempotente con modo de comprobación, pruebas en un host/namespace desechable y verificación de que Grumphya conserva DNS, OpenAI, correo, proxy y salud. Probar desde conector, probe y worker el acceso a host/gateway, redes señuelo internas y otros contenedores; confirmar que probe/worker no pueden eludir el conector, que este no es un proxy abierto, que DNS se limita a resolvers explícitos por UDP/TCP 53, y que IPv6 queda deshabilitado/bloqueado en Docker y host. No se debe ejecutar un scan real ni publicar el executor hasta superar los casos de red pendientes descritos en [test-plan.md](test-plan.md#fixtures-y-gates), incluidas denegaciones IPv4/IPv6, destinos no autorizados, DNS rebinding/redirecciones y medición en el VPS. Las muestras entregadas no prueban el efecto de estas reglas porque todavía no se han aplicado.

### Recolector de capacidad del VPS

El script `apps/prototype-desarrollo-seguro/prototype-desarrollo-seguro-worker/scripts/measure-vps-capacity.mjs` recoge muestras de solo lectura del host Linux: load average, memoria disponible, swap total y usado, espacio disponible en `/`, número de CPU, y uso/PIDs de contenedores que informa `docker stats`. Resume percentiles y mínimos. La frecuencia de muestreo es configurable entre 5 y 60 segundos (por defecto, 10), y la duración entre 60 y 3600 segundos (por defecto, 300). Puede hacer, de forma opcional, un `GET` solo a `https://grumphya.com/api/health`; no sigue redirecciones y trata cualquier respuesta distinta de 200, incluidos los 3xx, como error. Resume número de solicitudes correctas/erróneas y p95 de latencia de las respuestas 200. El health GET no implementa DNS/IP pinning: si la resolución DNS estuviera comprometida podría alcanzar una dirección interna. Es un helper local de capacidad, no el futuro scanner controlado, y solo debe ejecutarse con controles de egress que impidan conexiones a redes internas. No ejecuta comandos que cambien configuración, no inicia contenedores, no encola ni inicia scans y no evalúa los resultados de seguridad. La opción `--label=controlled-scan` solo etiqueta la ventana observada; no inicia una prueba. La opción `--output` crea un archivo JSON nuevo con permisos de propietario y falla si ya existe.

El recolector Node todavía **no se ha ejecutado en el VPS**. Requiere Linux y acceso a Docker para obtener métricas de contenedor; el health check es opcional. El JSON contiene nombres de contenedores, métricas del host y estructura/configuración básica del entorno. El archivo creado con `--output` usa permisos `0600` y no sobrescribe archivos, pero sin esa opción el JSON se imprime por stdout y puede terminar en logs; no lo adjuntar a CI ni a logs públicos, y proteger también cualquier artefacto guardado. Tras autorización para medir capacidad, una línea base puede tomarse así desde la raíz del repositorio:

```sh
node apps/prototype-desarrollo-seguro/prototype-desarrollo-seguro-worker/scripts/measure-vps-capacity.mjs \
  --label=baseline \
  --duration-seconds=300 \
  --interval-seconds=10 \
  --health-url=https://grumphya.com/api/health \
  --output=/tmp/ds-vps-capacity-baseline.json
```

Este p95 corresponde únicamente a la petición del endpoint de salud y no equivale a latencia de usuario ni mide la tasa de errores bajo tráfico o carga de escaneo. No reemplaza una prueba controlada de carga. La fase 0 sigue incompleta mientras falten mediciones con scan load y validación de firewall/egress.

Sin `--health-url`, no hace solicitudes de red. Usar `--label=controlled-scan` únicamente durante una prueba controlada que ya haya superado los gates de rúbrica, DNS/IP pinning, firewall/egress y capacidad. La ejecución real de esa prueba requiere autorización y el flujo operativo aprobado por separado; el recolector nunca la inicia. Revisar el JSON en almacenamiento con acceso controlado y consignar en el PR un resumen que no revele nombres de contenedores ni detalles innecesarios; adjuntar el artefacto solo si el destino tiene acceso restringido. El p95 del probe es solo la latencia del endpoint de salud, no la latencia p95 de usuarios en Grumphya; la evaluación de degradación y errores de la aplicación requiere métricas/monitorización complementarias.

Puerta: cero OOM y swapping sostenido, sin incremento material de errores ni degradación de latencia p95 de Grumphya frente a la línea base acordada, y suficiente espacio para resultados/backups. Si falla, reducir el presupuesto o dejar la captura pública deshabilitada; la ficha dirá no evaluable o caducado. No degradar Grumphya para sostener un sello.

## Seguridad y privacidad operativas

- Sin cookies de terceros, scripts, píxeles, fuentes, iframes ni recursos remotos en Grumphya ni en el sello. Clic y búsqueda son acciones explícitas bajo el mismo origen.
- Logs DS mínimos, sin HTML completo ni valores de cookies. Truncar/redactar direcciones y cabeceras sensibles, definir retención, impedir que destinos escaneados escriban logs descontrolados.
- Rate limit y cuota de consulta por origen y dominio; backpressure global. El scheduler de grumphya.com tiene prioridad acotada, sin monopolizar CPU.
- Métricas: duración y cola, antigüedad del último resultado, errores por control, denegaciones SSRF, carga/latencia del VPS y ocupación de DB. Alertar por stale prolongado, lease atascado y capacidad.
- Secretos DS distintos y rotables; no compartir claves de sesión, OpenAI, correo ni credenciales de Grumphya. Probe sin secretos de base.
- El escaneo desde el propio VPS de grumphya.com puede atravesar el IP público o el hairpin del proveedor. Probar que la ruta realmente toca la entrada pública y anotar el camino observado; si la red no lo permite, marcar no evaluable hasta resolverlo, sin sustituirla silenciosamente por una llamada interna.

## Release, smoke y reversión

El workflow actual de producción se lanza manualmente desde main con approve_production_deploy y PRODUCTION_DEPLOY_ENABLED=true. Conservar esta puerta. Antes de la aprobación de publicación, completar PR/CI, migración en entorno de prueba, pruebas de límites, carga y restauración. Una release incorpora los servicios DS en el Compose compartido; el humo valida rutas antiguas de Grumphya, landing, DS API, consulta, estado, un escaneo controlado y que la ficha académica siga identificada como demostración.

Preparar reversión de imagen/Compose que **no borre ni reinterprete** los scan_runs guardados. Cambios de esquema DS expansivos primero; no lanzar migraciones destructivas junto a la primera publicación. Si la DS API falla, retirar sus rutas/feature flag sin interrumpir Grumphya. Probar ese procedimiento en entorno representativo y documentar las órdenes exactas en doc/production.md cuando Luna implemente.

El dominio desarrolloseguro.com, repo, despliegue, instancia o volumen de datos propios y una sonda realmente externa pertenecen a una fase posterior.
