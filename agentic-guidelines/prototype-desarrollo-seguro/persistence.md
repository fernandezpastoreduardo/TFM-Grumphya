# Persistencia y ejecución horaria

## Estado de implementación

El paquete `apps/prototype-desarrollo-seguro/prototype-desarrollo-seguro-persistence/` ya contiene el aprovisionador idempotente de base/roles, migraciones SQL propias y `PostgresScanStore`. El almacén implementa frescura/singleflight de 60 minutos, leases, recuperación y finalización transaccional de runs/checks/métricas. Las funciones SQL validan leases y veredictos con `clock_timestamp()` de PostgreSQL. Existen pruebas locales, incluidas pruebas PostgreSQL con guardas de aislamiento. Esta implementación **no se ha ejecutado contra la base de producción** ni se ha integrado en el Compose/release; no se deben correr las credenciales/provisión productivas desde este trabajo.

La retención de 90 días está expresada en `ds_purge_expired_reports`, una rutina `SECURITY DEFINER` cuyo invocador autorizado es `ds_migrator`; API y worker no tienen permiso para ejecutarla. La rutina está instalada, pero todavía no hay tarea operativa programada. Su ejecución queda reservada al migrator bajo operación controlada. No hay API pública para admitir scans ni worker ejecutable/scheduler. El `ScanExecutor` sigue siendo un puerto sin implementación de red, por lo que no hay informes derivados de observaciones reales.

## Integridad de trabajos y resultados

La migración `003_guarded_worker_operations.sql` cierra localmente la vía de escritura directa: `ds_worker` no tiene permisos `INSERT` en tablas de resultados ni `UPDATE` en trabajos, y ejecuta funciones `SECURITY DEFINER` para claim, renovación, recuperación y finalización. La función de finalización fija `search_path`, carga el job bajo lease vigente usando `clock_timestamp()` de la base, deriva hostname/perfil/trigger de esa fila, valida forma y tamaño del resultado y recalcula el veredicto dentro de una operación transaccional. El catálogo `ds_profile_controls` tiene un trigger que bloquea `UPDATE` y `DELETE`; runtime no tiene DML y las nuevas filas/perfiles se incorporan mediante migraciones confiables. `controls-v1` conserva los nueve controles obligatorios y sus reglas originales. Un resultado `pass` de v1 solo se acepta si el perfil existe y todos sus IDs obligatorios están presentes como `required=true` y `status=pass`; un control obligatorio desconocido o incompleto se rechaza. Perfiles no catalogados no pueden emitir `pass`. La migración revoca la ejecución pública; el aprovisionamiento concede ejecución a `ds_worker` solo para esas rutinas.

Este cierre es código y evidencia de pruebas locales, no una migración productiva ejecutada ni autorización para escanear. Antes de producción, revisar SQL, grants efectivos y pruebas sobre una base aislada como parte del gate de release. API/worker runtime no pueden modificar informes fuera de la rutina.

La fase técnica 1 y el endurecimiento local de ingesta están completados. `scan-ingestion-policy.ts` valida scope, control, rutas/métodos y tipos/campos de evidencia, descarta claves no permitidas, deriva estados frente a predicados y reemplaza `summary`/`limitation` libres por texto generado. `004_scan_payload_guards.sql` y `005_controls_v2_route_coverage.sql` implementan los contratos versionados: v1 conserva su catálogo y criterios; v2 exige el conjunto completo de combinaciones host/ruta/método descrito en [controls-and-evidence.md](controls-and-evidence.md). Para `grumphya.com` el scope permite `/`, `/precios` y `/acreditaciones/DS-GRUMPHYA-2026-001`; otros dominios solo `/`. La suite PostgreSQL aislada tras migration 005 pasó 52/52, 0 omitidas, el 2 de noviembre de 2026. Esta verificación local no es migración productiva, autorización para escanear ni gate de red completado.

El contrato semántico compartido convierte `pass` con evidencia mínima ausente en `unknown`, deriva `fail` ante señales concluyentes (p. ej. certificado no válido, cabecera ausente, recurso fallido o cookie insegura), mantiene `unknown` cuando no se puede concluir y convierte `not_applicable` en `unknown` porque no hay justificación auditable implementada. La DB rechaza un `pass` directo que no satisfaga su predicado. En v2, el core y una validación diferida de la migración 005 exigen cobertura completa de checks para el scope declarado: tres checks host-level más siete por ruta (10/17/24 en scopes de 1/2/3 rutas). La cobertura se limita al scope declarado: un pass solo de `/` no afirma nada sobre otras rutas, por lo que el informe debe mostrar el scope. El caso v2 de `HEAD` 405/501 con redirección HTTPS confirmada y esquema final HTTPS se normaliza a `unknown`; v1 conserva su conducta original. Esta protección de integridad no autentica la evidencia: un worker comprometido aún podría fabricar valores permitidos, así que el futuro executor y su frontera de red forman parte de la base de confianza. El worker valida que el hostname reclamado sea normalizado antes de llamar a `executor.execute`. También contiene un adaptador DNS aislado que resuelve y valida A/AAAA por invocación, y un seam que configura una petición HTTPS HEAD pinned pero no la envía ni abre socket. El seam no es transporte/executor y no está probado contra socket o certificado real; no maneja timeouts HTTP, cancelación, bytes, respuestas ni redirects. El deadline DNS no cubre los timeouts de red. El deadline de cinco segundos limita la espera del consumidor, no cancela `dns.lookup`/`getaddrinfo`; el singleton de esta instancia del módulo admite como máximo dos resoluciones concurrentes entre instancias del adaptador por defecto y conserva cada plaza hasta que termina el resolver real, incluso tras el timeout del consumidor. Este cap no cubre llamadas DNS ajenas al adaptador ni copias del módulo. Antes de integrar hay que reservar capacidad del threadpool de libuv o usar un resolver dedicado, fijar límites globales de tasa/concurrencia e implementar y probar límites HTTP y revalidación en cada conexión/redirección. El executor real sigue bloqueado hasta probar pinning por conexión/redirección, firewall/egress y capacidad. No hay probe ni scans; las guardas de payload no son defensa SSRF.

## Seguridad del test de provisioning

La prueba `test:postgres` puede crear/eliminar una base y crear/alterar/eliminar roles PostgreSQL, que son globales al cluster. Solo debe optarse por ejecutarla con `DS_TEST_POSTGRES_ISOLATED=1` contra un **cluster PostgreSQL local dedicado a pruebas**, URL de conexión a loopback (`localhost`, `127.0.0.1` o `::1`) y nombre de base que empiece por `development_security_test`. El opt-in afirma que el cluster no contiene roles o datos de otros proyectos. No apuntar a la instancia compartida de Grumphya ni a producción, aunque se use una base con prefijo de test.

## Seguridad del aprovisionador manual

El comando `provision-database` del paquete acepta `DS_PROVISION_ADMIN_URL` como URL administrativa y puede crear/modificar roles globales `ds_*`, además de crear la base indicada. Es una operación manual: no se invoca desde CI ni Compose y actualmente no comprueba que el destino sea local ni exige un opt-in de aislamiento. Hasta añadir un gate explícito de destino y opt-in para ese comando, usarlo **solo contra un cluster local dedicado**; no apuntarlo al cluster compartido de Grumphya ni a producción. Una futura provisión compartida/productiva requiere autorización y un flujo separado y controlado, con el gate correspondiente; no reutilizar el CLI actual sin esas salvaguardas.

## Frontera de datos

Usar una **base lógica desarrollo_seguro y roles propios dentro de la instancia PostgreSQL existente**. Se comparte proceso, almacenamiento físico, TLS y VPS; no se comparten tablas, usuario de runtime, migrador ni credenciales de Grumphya. API y worker emplean pools pequeños y roles de mínimo privilegio. Las migraciones de Desarrollo Seguro viven en su app y se ejecutan como job de la misma release. La provisión de base/roles para un volumen ya existente es una tarea administrativa idempotente y auditada, no un script de initdb que solo funcionaría al crear el volumen. No hay claves foráneas a cuentas, ideas o sesiones de Grumphya.

## Cola y single flight

El endpoint y el scheduler llaman al mismo EnsureFreshScan en una transacción. La frescura y la reutilización se particionan por hostname y `profile_version`: un informe `controls-v1` no satisface una solicitud para `controls-v2`, y el historial anterior conserva su perfil original. Primero consultan el último run completo del perfil vigente. Si `completed_at` está dentro de los últimos 60 minutos, devuelven caché. Si no, intentan insertar un job activo; la restricción única resuelve carreras entre clics, búsquedas y scheduler. El worker reclama trabajos con bloqueo de fila tipo `FOR UPDATE SKIP LOCKED`, asigna lease corto y heartbeat. Al caducar el lease, otro worker puede recuperar; la finalización inserta run/checks y marca job completed en una única transacción. Repetir el cierre con el mismo job no duplica runs.

El scheduler consulta solo dominios monitored y calcula due_at a partir del último resultado completo y del último intento; limita reintentos ante fallos para no generar una tormenta horaria. Un fallo del propio worker puede reintentarse con backoff acotado; una respuesta de rechazo del dominio se registra como inconclusive y espera a la siguiente ventana. La hora de publicación no depende de cron exacto: después de 60 minutos sin resultado completo el informe ya es stale aunque el job se retrase.

## Retención y borrado

Por defecto, conservar informes y checks públicos 90 días para trazabilidad; datos de jobs fallidos/diagnósticos operativos 7 días; métricas agregadas 90 días. No guardar HTML, capturas, cuerpos de respuesta, valores de Cookie/Set-Cookie, parámetros de consulta, tokens ni IP de visitantes. El host consultado se guarda solo si el scan fue admitido; una búsqueda sin scan no crea fila. Permitir opt-out administrativo y purga de diagnósticos on_demand conforme a política documentada; una petición de exclusión no borra la evidencia de un incidente operativo que deba conservarse por obligación concreta. Revisar estos plazos antes de producción. La función `ds_purge_expired_reports` puede ejecutarse por `ds_migrator` bajo operación controlada; API y worker no tienen `EXECUTE`. La tarea de mantenimiento todavía no existe y debe definirse/probarse antes de activar retención automática.

Backups: pg_dump de desarrollo_seguro verificable y restauración aislada. Aunque el dump sea separado, el volumen y el fallo físico de PostgreSQL siguen compartidos con Grumphya. El release debe probar que migraciones y rollback de código no corrompen datos existentes.
