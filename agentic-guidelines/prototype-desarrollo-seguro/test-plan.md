# Plan de TDD y verificación de la fase operativa

## Método

La implementación local actual cuenta con pruebas unitarias/de integración del core, almacenamiento, health API, lecturas públicas de estado/informe y processor. El incremento PostgreSQL requiere un cluster local dedicado y opt-in: `DS_TEST_POSTGRES_ISOLATED=1`, `DS_TEST_DATABASE_URL` apuntando a loopback (`localhost`, `127.0.0.1` o `::1`) y base de administración bajo el prefijo operativo `development_security_test_`. La URL debe ir sin query ni fragmento: parámetros como `?host=` pueden sobreescribir el hostname de la URL y están prohibidos. La prueba puede crear y borrar roles globales; el opt-in declara que el cluster está aislado y el operador debe verificarlo, porque la guardia de loopback no demuestra que sea dedicado. Nunca apuntar al cluster compartido de Grumphya ni al productivo, aunque la URL seleccione una base de test.

**Estado verificado el 3 de noviembre de 2026:** después de aplicar la migración 006, la suite PostgreSQL aislada pasó 65/65, con 0 omitidas. La suite del paquete API pasó 52/52, incluidas comprobaciones HTTP con listener de loopback y servicio stub local; estas pruebas no usan base de datos ni red externa. La suite PostgreSQL aislada indicada arriba es una ejecución separada. Repetir el conjunto aislado en los gates previos a cualquier release.

Los siguientes incrementos siguen Red → Green → Refactor con tests que expresen el contrato observable antes del código. Priorizar los riesgos que pueden causar daños al VPS o mostrar un aprobado falso: SSRF, límites de escaneo, caducidad, concurrencia, privacidad y aislamiento de Grumphya. Usar reloj, DNS, transporte y navegador inyectables; CI trabaja con fixtures locales y **nunca escanea dominios públicos reales**. Pruebas con grumphya.com se reservan para un smoke controlado tras la preparación operativa.

## Fixtures y gates

Crear servidores HTTP/TLS de prueba controlados para cada resultado y una red de test que modele IPs prohibidas. Los tests de SSRF deben observar conexiones realmente bloqueadas, no solo el valor de una función de validación. Cuando exista la topología aislada del executor, probar explícitamente desde cada rol (conector, probe y worker) los intentos de conexión a la gateway de sus bridges y a servicios que escuchen en el host por IPv4 e IPv6; el resultado debe ser denegación, salvo excepciones mínimas documentadas. Comprobar además que probe y worker no pueden salir directamente ni usar al conector como proxy abierto para dominios, puertos o métodos no autorizados, que el conector solo admite el origen/hostname aprobado, y que no hay bypass entre redes/roles. Verificar los bloqueos en `INPUT` para destinos del host y en `DOCKER-USER`/`FORWARD` para tráfico reenviado; probar también DNAT y hairpin a Caddy según la topología seleccionada. Usar una red/namespace desechable con servicios señuelo y evidencia de que ningún paquete llega a destinos denegados. Estas pruebas siguen pendientes: no hay executor ni política aplicada. Ejecutar navegador en contenedor con proxy de egreso simulado; comprobar que registrar un intento a un tercero no produce una solicitud efectiva. Usar respuestas deterministas, tamaños adversarios y un reloj falso. Una prueba de punta a punta cubre el flujo completo desde clic/búsqueda hasta informe, con trabajo de escaneo local en cola.

Antes de liberar, repetir en cluster aislado las pruebas PostgreSQL de integridad/ingesta descritas en [persistence.md](persistence.md), completar las rúbricas pendientes, superar firewall/egress y pruebas de capacidad, y ejecutar los gates existentes del monorepo, tests DS, revisión de accesibilidad, verificación CSP/orígenes y pruebas de carga. `controls-v3` y su gate HTTPS de DS-HDR-01 están implementados y validados localmente, sin alterar el historial ni comportamiento de `controls-v1`/`controls-v2`. El evaluador `security-headers-v1` aún no está conectado a la recolección de evidencia real; necesita integración y pruebas de red antes de considerarse operativo. El smoke de producción hará un número explícito y pequeño de solicitudes a grumphya.com; no debe correr por cada PR. Guardar resultados y umbrales de carga en el PR. Un falso aprobado, escape de red o degradación material de Grumphya bloquea publicación.
