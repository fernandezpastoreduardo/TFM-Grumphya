# Plan de TDD y verificación de la fase operativa

## Método

Luna implementará incrementos Red → Green → Refactor con tests que expresen el contrato observable antes del código. Priorizar los riesgos que pueden causar daños al VPS o mostrar un aprobado falso: SSRF, límites de escaneo, caducidad, concurrencia, privacidad y aislamiento de Grumphya. Usar reloj, DNS, transporte y navegador inyectables; CI trabaja con fixtures locales y **nunca escanea dominios públicos reales**. Pruebas con grumphya.com se reservan para un smoke controlado tras la preparación operativa.

## Matriz obligatoria

| Área                    | Casos mínimos y resultado esperado                                                                                                                                                                                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Normalización/admisión  | Host IDNA normalizado; URLs, IP literales, puertos, credenciales, rutas, fragmentos, host malformado y dominios prohibidos se rechazan. No hay solicitud saliente antes de la admisión.                                                                                |
| SSRF                    | A/AAAA privada, loopback, enlace local, multicast, metadata, DNS rebinding, CNAME a interno, redirección a interno/puerto no permitido, IPv6 y cadenas de redirección se bloquean antes de conectar. La defensa de red deniega lo que la validación lógica deje pasar. |
| Límite de impacto       | Solo HEAD/GET; robots para rutas; tope de páginas, redirecciones, bytes, tiempo, CPU/memoria/pids y concurrencia. Respuesta infinita o lenta se aborta; no se ejecutan formularios ni JS fuera del presupuesto.                                                        |
| Evidencia de transporte | Fixtures con DNS público, certificado válido/inválido, HTTPS, downgrade, redirección y TLS incompatible producen pass/fail/unknown conforme al perfil versionado.                                                                                                      |
| Cabeceras y cookies     | HSTS/CSP/anti-embed/referrer/nosniff y atributos de cookies evaluados por URL y contexto; evidencia redactada; cabecera ausente no se convierte en desconocido si era evaluable.                                                                                       |
| Navegador               | Contexto limpio y sin consentimiento detecta intentos a terceros, cookie de tercero, almacenamiento y mixed content; bloquea peticiones externas tras registrarlas. Repetición no hereda cookies; los fixtures no llaman a terceros reales.                            |
| Calidad                 | Páginas y recursos esenciales, enlaces de muestra, accesibilidad automática con límites: fallo reproducible, unknown por falta de cobertura y ninguna afirmación WCAG completa.                                                                                        |
| Veredicto               | Fallo obligatorio → no cumple; cualquier obligatorio unknown sin fallo → no evaluable; todos pass/not_applicable justificado → cumple; perfil cambiado no recalifica historial.                                                                                        |
| Frescura/cola           | 59:59 reutiliza; 60:00 caduca y solicita un solo trabajo; concurrencia e idempotencia; lease caducado/reintento; fallo del worker nunca conserva un vigente; scheduler solo para inscritos verificados.                                                                |
| API/UI                  | DTOs versionados y códigos 200/202/4xx; búsqueda y sello convergen en el mismo informe; estados loading, stale, no evaluable, error y ausencia; hora, versión, fuente same_vps y URLs muestreadas visibles.                                                            |
| Persistencia            | Migraciones, FK, unicidad, historial inmutable, transacción de publicación de resultado y mínima retención. Roles de DS no leen ni modifican tablas Grumphya, y viceversa.                                                                                             |
| Privacidad              | Grumphya y DS sin solicitudes a terceros ni cookies de terceros por cargar página/sello; no se guardan cuerpos, valores de cookies ni datos personales accidentales en evidencias o logs.                                                                              |
| Integración de release  | En entorno representativo, rutas Grumphya, ficha académica, landing, DS SPA, API y worker; servicios sin puertos host; recuperación de backup DS; reversión sin pérdida de historial.                                                                                  |

## Fixtures y gates

Crear servidores HTTP/TLS de prueba controlados para cada resultado y una red de test que modele IPs prohibidas. Los tests de SSRF deben observar conexiones realmente bloqueadas, no solo el valor de una función de validación. Ejecutar navegador en contenedor con proxy de egreso simulado; comprobar que registrar un intento a un tercero no produce una solicitud efectiva. Usar respuestas deterministas, tamaños adversarios y un reloj falso. Una prueba de punta a punta cubre el flujo completo desde clic/búsqueda hasta informe, con trabajo de escaneo local en cola.

Antes de liberar, ejecutar los gates ya existentes del monorepo, los tests DS, revisión de accesibilidad, verificación de CSP/orígenes y pruebas de carga con límites reales. El smoke de producción hará un número explícito y pequeño de solicitudes a grumphya.com; no debe correr por cada PR. Guardar resultados y umbrales de carga en el PR. Un falso aprobado, escape de red o degradación material de Grumphya bloquea publicación.
