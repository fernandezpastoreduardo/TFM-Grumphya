# Plan de TDD y verificación de la fase operativa

## Método

La implementación local actual cuenta con pruebas unitarias/de integración del core, almacenamiento, health API y processor. El incremento PostgreSQL requiere un cluster local dedicado y opt-in: `DS_TEST_POSTGRES_ISOLATED=1`, `DS_TEST_DATABASE_URL` apuntando a loopback (`localhost`, `127.0.0.1` o `::1`) y base de administración cuyo nombre empiece por `development_security_test`. La URL debe ir sin query ni fragmento: parámetros como `?host=` pueden sobreescribir el hostname de la URL y están prohibidos. La prueba puede crear y borrar roles globales; el opt-in certifica que el cluster está aislado. Nunca apuntar al cluster compartido de Grumphya ni al productivo, aunque la URL seleccione una base de test.

**Estado verificado el 2 de noviembre de 2026:** las pruebas PostgreSQL aisladas pasaron 50/50 y `pnpm quality:check` terminó con código 0. Repetir el conjunto aislado en los gates previos a cualquier release.

Los siguientes incrementos siguen Red → Green → Refactor con tests que expresen el contrato observable antes del código. Priorizar los riesgos que pueden causar daños al VPS o mostrar un aprobado falso: SSRF, límites de escaneo, caducidad, concurrencia, privacidad y aislamiento de Grumphya. Usar reloj, DNS, transporte y navegador inyectables; CI trabaja con fixtures locales y **nunca escanea dominios públicos reales**. Pruebas con grumphya.com se reservan para un smoke controlado tras la preparación operativa.

## Fixtures y gates

Crear servidores HTTP/TLS de prueba controlados para cada resultado y una red de test que modele IPs prohibidas. Los tests de SSRF deben observar conexiones realmente bloqueadas, no solo el valor de una función de validación. Ejecutar navegador en contenedor con proxy de egreso simulado; comprobar que registrar un intento a un tercero no produce una solicitud efectiva. Usar respuestas deterministas, tamaños adversarios y un reloj falso. Una prueba de punta a punta cubre el flujo completo desde clic/búsqueda hasta informe, con trabajo de escaneo local en cola.

Antes de liberar, repetir en cluster aislado las pruebas PostgreSQL de integridad/ingesta descritas en [persistence.md](persistence.md), completar las rúbricas pendientes, superar firewall/egress y pruebas de capacidad, y ejecutar los gates existentes del monorepo, tests DS, revisión de accesibilidad, verificación CSP/orígenes y pruebas de carga. El smoke de producción hará un número explícito y pequeño de solicitudes a grumphya.com; no debe correr por cada PR. Guardar resultados y umbrales de carga en el PR. Un falso aprobado, escape de red o degradación material de Grumphya bloquea publicación.
