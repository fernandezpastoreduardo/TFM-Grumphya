# CI/CD y seguridad de la imagen

El incidente del 28 de octubre de 2026 —recuperación SSH del VPS, actualización del helper y excepción restringida para la migración `034`— está documentado en [recuperación de acceso y despliegue](incident-vps-access-and-deployment-2026-10.md).

Los fallos de Compose y del preflight de migraciones del 29 de octubre de 2026 están resumidos en [fallos recientes de CI](ci-failures-2026-10-29.md).

El workflow `.github/workflows/ci.yml` se ejecuta en pull requests y mediante `workflow_dispatch`; no tiene un disparador `push`, así que ningún push inicia Actions automáticamente. Los jobs usan `ubuntu-24.04` para evitar cambios imprevistos de imagen y avisos por migraciones de `ubuntu-latest`. Tras checkout, el job `quality-and-e2e` ejecuta `node scripts/test-container-security-policy.mjs` antes de configurar pnpm o instalar dependencias. Este preflight comprueba, entre otras políticas del contenedor, que `location = /` resuelva `/index.html` con `try_files` y no use `alias`, y que cada migración numerada desde `029_` inclusive empiece con `-- deployment-rollback-compatible: true`. Después fija Node mediante `.node-version` (`24.21.0`), pnpm (`12.5.1`) e instala desde `pnpm-lock.yaml` con `--frozen-lockfile`. El job prepara PostgreSQL/pgvector y ejecuta `pnpm quality:check`, que comprueba la alineación de versiones de React y el registro de migraciones SQL y luego corre formato, lint, typecheck, tests y build. Dependabot agrupa las actualizaciones de versión y seguridad de React para mantener `react` y `react-dom` coordinados. También prueba la política del despliegue y el helper del VPS con comandos Docker simulados, incluidos checksum, compatibilidad de migraciones y rollback. El mismo comando está en el hook Husky `pre-commit`, así un cambio que falle una puerta local se rechaza antes de crear el commit. `e2e` ejecuta Playwright en la imagen oficial `mcr.microsoft.com/playwright:v1.64.0-noble`, que incluye Chromium y sus dependencias del sistema; el paquete del proyecto está fijado por el lockfile a `1.64.0`. `supply-chain` espera a los dos jobs de prueba y al job de auditoría. El hook Husky `pre-push` ejecuta `pnpm migrations:check` en todos los pushes, pero solo ejecuta `pnpm test:e2e` cuando entre los destinos del push está `refs/heads/main`; así los pushes de ramas de trabajo no repiten E2E en cada worktree. Para preparar el navegador local, instala Chromium con `pnpm --filter @grumphya/web exec playwright install chromium`. CI no modifica ni formatea archivos automáticamente.

Los tests PostgreSQL reciben un servicio temporal `pgvector/pgvector:0.8.7-pg17`. Antes de la suite, `prepare-test-database.ts` habilita `vector` en `public` y comprueba que está disponible. Cada spec que necesita persistencia crea un esquema aleatorio, ejecuta las migraciones registradas en `apps/api/src/infrastructure/database/run-migrations.ts` y lo elimina al terminar. El registro es explícito: añadir un archivo `.sql` sin añadirlo a esa lista deja el esquema de pruebas incompleto, aunque el archivo se incluya en la imagen de producción. Por eso `pnpm quality:check` también ejecuta `pnpm migrations:check`, que compara el inventario de `apps/api/migrations/*.sql` con el registro del migrador; una migración nueva debe añadirse a ambos. La compatibilidad de rollback se valida aparte y no sustituye este control de coherencia. Playwright arranca API y web en puertos de test dedicados, con repositorios en memoria y el adaptador de evaluación simulado; no usa credenciales ni datos de desarrollo/producción. La suite E2E corre con un worker porque comparte ese servidor de prueba y sus contadores de rate limit. No configura un proveedor LLM en CI.

Para replicar localmente los tests SQL, usa una base PostgreSQL/pgvector desechable dedicada exclusivamente a pruebas. Define `TEST_DATABASE_URL` y las variables `*_TEST_DATABASE_URL` que consuman los specs para que apunten a esa base antes de ejecutar `prepare-test-database.ts` y `pnpm test`. No reutilices la base de desarrollo: los tests preparan la extensión y crean/eliminan esquemas temporales. CI usa un servicio efímero separado.

El Dockerfile separa las etapas `development` y `production`. Docker Compose selecciona `development`, que instala las dependencias completas para Vite, tests y desarrollo local. CI construye y comprueba `production`: compila la API en una etapa de build, instala solo sus dependencias de producción y omite los gestores de paquetes del contenedor final. Antes de escanearla con Trivy, CI ejecuta `scripts/test-production-image.mjs` dentro de la imagen y verifica que `NODE_ENV` sea `production`, que el proceso no use UID 0, que estén disponibles las dependencias de runtime de NestJS, bcryptjs, PostgreSQL y sharp, que la imagen incluya migraciones SQL y que no queden ejecutables npm, npx, Corepack, pnpm ni Yarn. Así el escaneo cubre la imagen ejecutable y no herramientas de desarrollo que no se despliegan. La base usa Node `24.21.0-trixie-slim`; el build de CI usa `--pull` para recibir la última reconstrucción publicada de esa versión. La etiqueta es mutable: `--pull` ayuda a recibir actualizaciones de seguridad, pero dos ejecuciones pueden usar distintos digests y no garantizan una reconstrucción idéntica. Para repetir exactamente un build debe registrarse y fijarse el digest de la imagen base.

El job `dependency-audit` empieza en paralelo con calidad y E2E, para detectar pronto fallos de auditoría. Ejecuta `pnpm audit --audit-level moderate` para todo el workspace y `pnpm audit --prod --audit-level high` para dependencias de producción. Trivy analiza las cuatro imágenes finales (API, web, PostgreSQL y Caddy) con severidad alta/crítica e `ignore-unfixed`. Durante el build paralelo de imágenes, una descarga única obtiene la base de vulnerabilidades de Trivy para reutilizarla en los análisis; la base Java se omite porque estos escaneos solo usan el detector `vuln`. Después, Trivy analiza las imágenes de una en una y reutiliza la misma caché local. El escaneo secuencial limita el espacio temporal usado al exportar capas de Docker; cada análisis conserva su propio registro y el job falla si cualquiera devuelve un error o detecta vulnerabilidades que superen el umbral. `--skip-version-check` y `--disable-telemetry` se usan juntas para suprimir el aviso de versión y desactivar las llamadas opcionales a `check.trivy.dev`, sin cambiar los resultados ni el umbral del análisis. El job `supply-chain` configura Buildx y selecciona su builder con `BUILDX_BUILDER`, compatible con las versiones de Compose del runner, y construye las cuatro imágenes en paralelo con `docker compose --parallel 4 ... build`; las etiquetas llevan el SHA del commit. Un override temporal habilita la caché remota de BuildKit solo para el build de Caddy, que es la parte lenta; el contexto de Compose de producción no cambia. La caché usa el backend `type=gha`, no crea artefactos de Actions ni cambia el bundle publicado, y su exportación está marcada `ignore-error=true`: si GitHub no permite guardar la caché, el build sigue siendo válido y solo tardará más la siguiente vez. La descarga de la base de Trivy sigue en paralelo con el build. Después escanea las imágenes construidas y arranca exactamente esas mismas imágenes con `compose.production.yaml`, secretos ficticios y volúmenes de prueba exclusivos del run. El smoke comprueba HTTPS local en Caddy, la ruta SPA (incluida `/`), `/api/health`, pgvector, `NODE_ENV=production`, que API y PostgreSQL no publiquen puertos y que PostgreSQL y avatares sobrevivan a recrear servicios. El healthcheck de `web` consulta ahora `/` directamente a Nginx para detectar también fallos de portada; el smoke mantiene además la comprobación de `/` a través de Caddy, que cubre el recorrido público. Si el smoke falla, conserva en la salida de Actions el estado de Compose, el estado de salud de `web` y sus últimos 100 registros. No llama a OpenAI ni a SMTP. La limpieza elimina únicamente los volúmenes etiquetados para la prueba; nunca ejecuta `down -v` ni `volume prune`. La imagen web ejecuta `nginx -t` durante su construcción. La imagen PostgreSQL conserva Debian Bookworm para no cambiar la plataforma del volumen existente, actualiza paquetes y recompila `gosu` 1.19 con Go 1.27.3. Caddy 2.11.7 se recompila con Go 1.27.3 y `golang.org/x/net` 0.60.0; la imagen final actualiza Alpine. Las versiones fuente se fijan a commits exactos y el escaneo no excluye archivos ni tipos de vulnerabilidad. Las etapas de compilación no entran en las imágenes finales. Dependabot propone actualizaciones semanales de dependencias y acciones. Ignora TypeScript `>=7.0.0` mientras el parser `typescript-eslint` no declare soporte para esa versión.

Los pull requests ejecutan las comprobaciones de CI. Un push a `main` no inicia Actions: el despliegue se solicita manualmente desde la pestaña Actions, seleccionando `main` y confirmando `approve_production_deploy`. Solo `fernandezpastoreduardo` puede iniciar el flujo o volver a ejecutar un run. También se requiere `PRODUCTION_DEPLOY_ENABLED=true` y los secretos SSH del VPS. `quality-and-e2e`, `e2e` y `dependency-audit` corren en paralelo; `supply-chain` espera a que los tres pasen. Dentro de `supply-chain`, Buildx compila en paralelo las imágenes etiquetadas por SHA mientras Trivy descarga una vez su base de vulnerabilidades; la caché GitHub de BuildKit se limita a Caddy. Después, Trivy analiza las imágenes secuencialmente con la misma caché de vulnerabilidades, lo que reduce el espacio temporal requerido para exportar capas. `--skip-version-check` y `--disable-telemetry` se usan juntas para suprimir el aviso de versión y desactivar las llamadas opcionales a `check.trivy.dev`, sin cambiar los resultados del escaneo. El smoke valida esas mismas imágenes. En la vista del job se distinguen ahora `Save scanned release images`, `Assemble production release bundle`, `Preflight production deployment` y `Deploy and verify`; el helper del VPS registra hitos al recibir/verificar el bundle, validar migraciones y configuración, cargar imágenes y comenzar la actualización de Compose. El job empaqueta el bundle y lo envía al VPS sin reconstruir ni descargar tags mutables. Actions ya no sube el bundle a GitHub: antes solo lo archivaba después de desplegar y comprobar públicamente una versión sana, de modo que no consumía cuota cuando CI fallaba, pero retenía copias grandes redundantes y podía hacer que una publicación ya activa apareciera como fallida si se agotaba la cuota. Para Caddy, Compose usa `docker/Caddy.Dockerfile`, que recompila el binario parcheado y actualiza Alpine; `PROXY_IMAGE` apunta a la imagen escaneada y el helper arranca con `--no-build`. El helper root-owned valida el paquete y las migraciones, conserva la release anterior, espera healthchecks y permite rollback. No hay publicación a un registry. Consulta [production.md](production.md) para prerrequisitos, permisos SSH/sudoers, huella del host, activación y límites operativos. Los tests de CI cubren políticas, seguridad de contenedores, arranque con imágenes/datos desechables y rollback simulado. Los jobs `quality-and-e2e`, `e2e`, `dependency-audit`, `supply-chain` y `deploy-production` permiten distinguir fallos de calidad, navegador, auditoría, imagen y publicación en Actions. Todas las GitHub Actions están fijadas a SHA inmutables con etiquetas legibles; Dependabot propone actualizaciones semanales. Trivy `v0.76.0` se instala mediante `aquasecurity/setup-trivy` `v0.2.6`, fijado por SHA.

## Ejecución local equivalente

```sh
pnpm install --frozen-lockfile
pnpm --filter @grumphya/api exec tsx scripts/prepare-test-database.ts
pnpm quality:check
pnpm --filter @grumphya/web exec playwright install chromium
pnpm test:e2e
node scripts/test-deploy-policy.mjs
node scripts/test-container-security-policy.mjs
bash -n docker/vps-deploy.sh scripts/test-vps-deploy.sh
bash scripts/test-vps-deploy.sh
SHA=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
bash scripts/test-production-compose.sh "$SHA" --validate-only
pnpm audit --audit-level moderate
pnpm audit --prod --audit-level high
docker build --pull --target production --tag "grumphya-api:$SHA" .
docker build --pull --target web-production --build-arg "DEPLOY_SHA=$SHA" --tag "grumphya-web:$SHA" .
docker build --pull --target database-production --tag "grumphya-database:$SHA" .
docker build --pull --file docker/Caddy.Dockerfile --tag "grumphya-proxy:$SHA" .
node scripts/test-production-image.mjs "grumphya-api:$SHA"
bash scripts/test-production-compose.sh "$SHA"
# Solo si las imágenes se construyeron exclusivamente para esta prueba:
docker image rm "grumphya-api:$SHA" "grumphya-web:$SHA" "grumphya-database:$SHA" "grumphya-proxy:$SHA"
```

La prueba de contrato necesita Docker y una imagen de producción ya construida. Ejecuta un proceso Node dentro del contenedor, no arranca el servicio ni se conecta a PostgreSQL; comprueba únicamente que el artefacto contiene sus dependencias de runtime y migraciones, usa un usuario no-root y excluye los gestores de paquetes. El smoke de Compose completo necesita Docker y las cuatro imágenes etiquetadas con el mismo SHA. Usa un proyecto, redes y volúmenes temporales aislados, y enlaza los puertos HTTP/HTTPS altos únicamente a `127.0.0.1`. Hace las peticiones a `https://localhost` con un certificado interno de Caddy y utiliza secretos ficticios; no contacta un VPS, OpenAI ni SMTP. Comprueba la portada pública en `/`. Si falla, imprime `docker compose ps`, el estado de salud del contenedor web y sus últimos 100 registros antes de limpiar el stack. Asegúrate de que esos puertos y subredes estén disponibles. Si uno está ocupado, el smoke falla sin parar ni borrar el recurso que lo ocupa. Al terminar elimina únicamente sus contenedores/redes y los volúmenes que llevan su etiqueta temporal; no elimina imágenes. `--validate-only` solo valida Compose y no necesita el daemon.

El comando de preparación de PostgreSQL requiere las variables de test descritas arriba; si no están configuradas, los tests que dependen de PostgreSQL pueden omitirse. En GitHub Actions, el workflow define todas las URLs de test contra su servicio efímero.

El escaneo Trivy se ejecuta en GitHub Actions. Para revisar la misma imagen local, constrúyela con `--target production` y ejecuta `trivy image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed grumphya-ci:local`.
