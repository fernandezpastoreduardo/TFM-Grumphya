# CI/CD y seguridad de la imagen

El workflow `.github/workflows/ci.yml` se ejecuta en pull requests y al publicar en `main`; un push a otra rama no lo inicia por sí solo. Los jobs usan `ubuntu-24.04` para evitar cambios imprevistos de imagen y avisos por migraciones de `ubuntu-latest`. Fija Node mediante `.node-version` (`24.21.0`), pnpm (`12.5.1`) e instala desde `pnpm-lock.yaml` con `--frozen-lockfile`. El job `quality-and-e2e` prepara PostgreSQL/pgvector y ejecuta `pnpm quality:check`, que primero comprueba que `react` y `react-dom` estén fijados a la misma versión exacta y luego corre formato, lint, typecheck, tests y build. Dependabot agrupa las actualizaciones de versión y seguridad de ambos paquetes para mantenerlos coordinados. También prueba la política del despliegue y el helper del VPS con comandos Docker simulados, incluidos checksum, compatibilidad de migraciones y rollback. El mismo comando está en el hook Husky `pre-commit`, así un cambio que falle una puerta local se rechaza antes de crear el commit. Tras instalar Chromium, CI ejecuta Playwright; el hook Husky `pre-push` corre también `pnpm test:e2e` antes de publicar. Para preparar el navegador local, instala Chromium con `pnpm --filter @grumphya/web exec playwright install chromium`. CI no modifica ni formatea archivos automáticamente.

Los tests PostgreSQL reciben un servicio temporal `pgvector/pgvector:0.8.7-pg17`. Antes de la suite, `prepare-test-database.ts` habilita `vector` en `public` y comprueba que está disponible. Cada spec que necesita persistencia crea un esquema aleatorio, ejecuta migraciones en él y lo elimina al terminar. Playwright arranca API y web en puertos de test dedicados, con repositorios en memoria y el adaptador de evaluación simulado; no usa credenciales ni datos de desarrollo/producción. La suite E2E corre con un worker porque comparte ese servidor de prueba y sus contadores de rate limit. No configura un proveedor LLM en CI.

Para replicar localmente los tests SQL, usa una base PostgreSQL/pgvector desechable dedicada exclusivamente a pruebas. Define `TEST_DATABASE_URL` y las variables `*_TEST_DATABASE_URL` que consuman los specs para que apunten a esa base antes de ejecutar `prepare-test-database.ts` y `pnpm test`. No reutilices la base de desarrollo: los tests preparan la extensión y crean/eliminan esquemas temporales. CI usa un servicio efímero separado.

El Dockerfile separa las etapas `development` y `production`. Docker Compose selecciona `development`, que instala las dependencias completas para Vite, tests y desarrollo local. CI construye y comprueba `production`: compila la API en una etapa de build, instala solo sus dependencias de producción y omite los gestores de paquetes del contenedor final. Antes de escanearla con Trivy, CI ejecuta `scripts/test-production-image.mjs` dentro de la imagen y verifica que `NODE_ENV` sea `production`, que el proceso no use UID 0, que estén disponibles las dependencias de runtime de NestJS, bcryptjs, PostgreSQL y sharp, que la imagen incluya migraciones SQL y que no queden ejecutables npm, npx, Corepack, pnpm ni Yarn. Así el escaneo cubre la imagen ejecutable y no herramientas de desarrollo que no se despliegan. La base usa Node `24.21.0-trixie-slim`; el build de CI usa `--pull` para recibir la última reconstrucción publicada de esa versión. La etiqueta es mutable: `--pull` ayuda a recibir actualizaciones de seguridad, pero dos ejecuciones pueden usar distintos digests y no garantizan una reconstrucción idéntica. Para repetir exactamente un build debe registrarse y fijarse el digest de la imagen base.

El job `supply-chain` ejecuta dos auditorías del lockfile: `pnpm audit --audit-level moderate` revisa dependencias de producción y desarrollo en todo el workspace, y bloquea vulnerabilidades moderadas o superiores; `pnpm audit --prod --audit-level high` revisa las dependencias de producción y bloquea hallazgos altos o críticos. Esto incluye las herramientas de pruebas, aunque no formen parte de la imagen final. Para resolver los hallazgos actuales se actualizaron Vitest a `4.1.12` en API y web y se fijó `shell-quote` en `1.12.0` mediante un override del workspace. Trivy analiza las cuatro imágenes finales (API, web, PostgreSQL y Caddy) con severidad alta/crítica y `ignore-unfixed`, por lo que bloquea los hallazgos para los que hay una corrección disponible. Después de escanearlas, CI arranca esas mismas imágenes con `compose.production.yaml`, secretos ficticios y volúmenes de prueba con nombres y etiquetas exclusivos del run. Comprueba HTTPS local en Caddy, la ruta SPA, `/api/health`, pgvector, `NODE_ENV=production`, que API y PostgreSQL no publiquen puertos y que los datos de PostgreSQL y avatares sobrevivan a recrear la base, migraciones, API, web y proxy. Para Caddy comprueba los puertos publicados y sus enlaces al host: que la imagen declare un puerto como expuesto (por ejemplo, `2019/tcp`, usado por su administración) no significa que Compose lo publique. No llama a OpenAI ni a SMTP. La limpieza elimina únicamente los volúmenes que llevan la etiqueta del stack temporal; nunca ejecuta `down -v` ni `volume prune`. La imagen web también ejecuta `nginx -t` durante su construcción, para rechazar antes del despliegue errores de sintaxis como una expresión regular de Nginx sin comillas. La imagen de PostgreSQL conserva Debian Bookworm para no cambiar la plataforma del volumen existente, actualiza sus paquetes y recompila `gosu` 1.19 con Go 1.27.3. El proxy usa Caddy 2.11.7 recompilado con Go 1.27.3 y `golang.org/x/net` 0.60.0; la etapa final también actualiza los paquetes Alpine con `apk upgrade --no-cache`. Ambas fuentes se comprueban contra su commit exacto; no se excluyen archivos ni tipos de vulnerabilidad del escaneo. Las etapas de compilación no entran en las imágenes finales. Dependabot propone actualizaciones semanales de dependencias y acciones. Para evitar que abra una actualización incompatible, Dependabot ignora TypeScript `>=7.0.0` mientras el parser `typescript-eslint` no declare soporte para esa versión; la actualización se puede reconsiderar cuando el parser la admita.

El despliegue automático opcional desde GitHub Actions está implementado para pushes a `main`, pero permanece apagado hasta que `PRODUCTION_DEPLOY_ENABLED` se habilite y se configuren los secretos SSH del VPS. El job construye y escanea API, web, PostgreSQL y Caddy; el smoke de Compose valida luego esas mismas imágenes antes de que se empaqueten por SHA y se envíen al VPS sin reconstruir ni descargar tags mutables. Para Caddy, Compose usa por defecto `docker/Caddy.Dockerfile`, que reconstruye el binario parcheado y actualiza Alpine; en el bundle de release, `PROXY_IMAGE` apunta al tag SHA de la imagen Caddy escaneada y el helper ejecuta Compose con `--no-build`, sin sustituirla por una reconstrucción local. Un helper root-owned valida el paquete y las migraciones, mantiene la release anterior, espera healthchecks y permite rollback. No hay publicación a un registry. Consulta [production.md](production.md) para prerrequisitos, permisos SSH/sudoers, verificación de host, activación explícita y límites operativos. Los tests de CI incluyen `scripts/test-deploy-policy.mjs`, `scripts/test-container-security-policy.mjs`, `scripts/test-production-compose.sh` y `scripts/test-vps-deploy.sh`; cubren los guards de políticas de despliegue y seguridad de contenedores, el arranque con imágenes y datos desechables y el rollback con Docker simulado. Las conclusiones de una ejecución se separan por los jobs `quality-and-e2e`, `supply-chain` (auditoría, build, escaneo y smoke de producción) y `deploy-production`. Esto permite distinguir un fallo de CI de uno de publicación directamente en la vista de Actions, sin exportar logs ni introducir un servicio de pago de métricas. Se mantienen despliegues para todos los pushes que cumplan la política de `main`, incluidos cambios documentales, para conservar la regla de publicar la revisión exacta del push. Todas las GitHub Actions están fijadas a SHA inmutables y conservan una etiqueta de versión legible en el workflow; Dependabot propone semanalmente sus actualizaciones en pull requests revisables. El escaneo usa Trivy `v0.76.0` mediante `aquasecurity/trivy-action` `v0.36.0`, también fijada por SHA.

## Ejecución local equivalente

```sh
pnpm install --frozen-lockfile
pnpm --filter @grumphya/api exec tsx scripts/prepare-test-database.ts
pnpm quality:check
pnpm --filter @grumphya/web exec playwright install chromium
pnpm test:e2e
node scripts/test-deploy-policy.mjs
node scripts/test-container-security-policy.mjs
bash -n docker/vps-deploy.sh scripts/test-vps-deploy.sh
bash scripts/test-vps-deploy.sh
SHA=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
bash scripts/test-production-compose.sh "$SHA" --validate-only
pnpm audit --audit-level moderate
pnpm audit --prod --audit-level high
docker build --pull --target production --tag "grumphya-api:$SHA" .
docker build --pull --target web-production --build-arg "DEPLOY_SHA=$SHA" --tag "grumphya-web:$SHA" .
docker build --pull --target database-production --tag "grumphya-database:$SHA" .
docker build --pull --file docker/Caddy.Dockerfile --tag "grumphya-proxy:$SHA" .
node scripts/test-production-image.mjs "grumphya-api:$SHA"
bash scripts/test-production-compose.sh "$SHA"
# Solo si las imágenes se construyeron exclusivamente para esta prueba:
docker image rm "grumphya-api:$SHA" "grumphya-web:$SHA" "grumphya-database:$SHA" "grumphya-proxy:$SHA"
```

La prueba de contrato necesita Docker y una imagen de producción ya construida. Ejecuta un proceso Node dentro del contenedor, no arranca el servicio ni se conecta a PostgreSQL; comprueba únicamente que el artefacto contiene sus dependencias de runtime y migraciones, usa un usuario no-root y excluye los gestores de paquetes. El smoke de Compose completo necesita Docker y las cuatro imágenes etiquetadas con el mismo SHA. Usa un proyecto, redes y volúmenes temporales aislados, y enlaza los puertos HTTP/HTTPS altos únicamente a `127.0.0.1`. Hace las peticiones a `https://localhost` con un certificado interno de Caddy y utiliza secretos ficticios; no contacta un VPS, OpenAI ni SMTP. Asegúrate de que esos puertos y subredes estén disponibles. Si uno está ocupado, el smoke falla sin parar ni borrar el recurso que lo ocupa. Al terminar elimina únicamente sus contenedores/redes y los volúmenes que llevan su etiqueta temporal; no elimina imágenes. `--validate-only` solo valida Compose y no necesita el daemon.

El comando de preparación de PostgreSQL requiere las variables de test descritas arriba; si no están configuradas, los tests que dependen de PostgreSQL pueden omitirse. En GitHub Actions, el workflow define todas las URLs de test contra su servicio efímero.

El escaneo Trivy se ejecuta en GitHub Actions. Para revisar la misma imagen local, constrúyela con `--target production` y ejecuta `trivy image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed grumphya-ci:local`.
