# Usuarios, credenciales y secretos

## Lo que existe ahora

- GitHub: repositorio privado `fernandezpastoreduardo/TFM-Grumphya`; el acceso se realiza mediante la sesión SSH/CLI ya configurada en el equipo. No copiar ni documentar su token o clave privada.
- Desarrollo Docker PostgreSQL: base/rol `grumphya_dev`, puerto enlazado solo a `127.0.0.1:5433`; `pnpm db:setup` genera una contraseña aleatoria en `.env.docker` con permisos `0600`. Mantén también `.env.openai`, `.env` y, al configurar SMTP, `.env.mail` con permisos `0600`; están ignorados por Git.
- PostgreSQL Homebrew preexistente: la base y extensión creadas en la verificación inicial permanecen en `5432`; el flujo de la app usa el contenedor independiente en `5433`.
- Cuentas Grumphya: el alta con plan requiere verificar el correo y confirmar la contratación simulada antes de activar cuenta, suscripción y sesión. El login usa alias o correo y contraseña; el restablecimiento envía un enlace de un solo uso. La autenticación de dos factores sigue pendiente. Revisa [plan de seguridad del registro y similitud](security-and-similarity-roadmap.md) para los controles y límites restantes.
- Embeddings: adaptador OpenAI API `text-embedding-3-small` implementado. En desarrollo, `OPENAI_API_KEY` se configura en el archivo local ignorado `.env`; el evaluador requiere además `EVALUATION_PROVIDER=openai` en `.env.openai`. Para producción, usa archivos separados en `.secrets/`: `grumphya_env` (firmas de autenticación), `postgres_admin_settings` (contraseña bootstrap, solo para PostgreSQL), `database_settings` (base, usuario y contraseña del rol de runtime), `openai_settings`, `openai_key`, `mail_settings`, `admin_settings` (solo para aprovisionamiento explícito de Jappy), la CA interna y certificados/llaves TLS de los servicios. Las plantillas vacías `.secrets/*.example` documentan sus claves. El Compose monta cada archivo como secreto solo en los servicios que lo necesitan. No pongas OpenAI, SMTP o contraseñas de usuario en `VITE_*`, argumentos de build o logs. Es separación de archivos, no cifrado en reposo ni sustituto de controlar el VPS y sus copias. Consulta [preparación para producción](production.md) para permisos, alta y rotación.
- La moderación de avatares reutiliza `OPENAI_API_KEY` y llama desde el servidor a `omni-moderation-latest`; no se configura ni expone una clave adicional al navegador. El editor recorta en cliente a JPEG cuadrado de 128×128; el backend vuelve a validarlo, lo normaliza a WebP de 128×128 y envía ese resultado a OpenAI, no los bytes originales. Sin clave o si el proveedor/moderador falla, la subida falla de forma cerrada (no se guarda el avatar). La política de privacidad versión 5 describe este tratamiento; confirmar en producción los contratos y la configuración efectiva de proveedores.

### Rotación en Docker local

- Tras cambiar `ACCESS_TOKEN_SECRET`, `ANONYMOUS_IP_HMAC_SECRET` o la configuración/clave OpenAI, recrea la API para que vuelva a leer los archivos montados. Rotar `ACCESS_TOKEN_SECRET` invalida los access tokens ya emitidos; rotar `ANONYMOUS_IP_HMAC_SECRET` cambia la señal antiabuso de los perfiles anónimos existentes.
- Cambiar `GRUMPHYA_DB_PASSWORD` en `.env.docker` no modifica la contraseña del rol PostgreSQL en un volumen ya inicializado. Coordina el cambio con `ALTER ROLE` en la base existente y recrea la API con el nuevo secreto. No elimines el volumen como mecanismo de rotación.
- Los secretos respaldados por archivos locales requieren rotación manual. En el Compose de producción son archivos del host montados como secretos de solo lectura, no un secret manager: protégelos con permisos del sistema y copia cifrada, y sigue el procedimiento de [production.md](production.md) para rotarlos sin eliminar volúmenes.

### Secretos del VPS

- `postgres_admin_settings` contiene únicamente `POSTGRES_ADMIN_PASSWORD` y solo se monta en `db`. `database_settings` contiene `PGDATABASE`, `PGUSER` y `GRUMPHYA_DB_PASSWORD`; este rol es propietario de la base pero no tiene privilegios de superusuario. API, migrador y aprovisionador de Jappy comparten el rol de runtime. Para rotar una contraseña, abre una sesión local de `psql` como bootstrap y usa `\password postgres` o `\password <PGUSER>`; actualiza el archivo de secreto correspondiente y recrea los servicios que lo usan. Cambiar un archivo no altera contraseñas de roles en un volumen ya inicializado. El procedimiento está en [production.md](production.md).
- `grumphya_env` contiene únicamente `ACCESS_TOKEN_SECRET` y `ANONYMOUS_IP_HMAC_SECRET`. Rotar el primero invalida access tokens; rotar el segundo cambia la señal antiabuso anónima.
- `openai_key` y `mail_settings` contienen únicamente sus respectivas credenciales externas. `openai_settings` contiene selección de proveedor y opciones no secretas.
- `admin_settings` contiene `ADMIN_PASSWORD` y solo se monta al ejecutar `admin-provision`. El arranque normal de la API no lee ni modifica esa cuenta. Para cambiar contraseña y revocar sus sesiones deliberadamente, usa el comando `--change-password` documentado en [production.md](production.md).

## Cómo tratar secretos futuros

- En local, guarda secretos en un gestor de credenciales del sistema o archivo ignorado por Git con permisos de usuario. No reutilices `.env` compartidos ni los adjuntes a issues.
- Para esta caja de producción, Compose monta archivos protegidos del VPS en modo solo lectura; no hay integración con un secret manager. Restringe el acceso SSH y los permisos de esos archivos, y cifra las copias externas.
- Las contraseñas de usuarios se guardan con `bcryptjs` cost 12 aplicado a un prehash SHA-256 hexadecimal de la contraseña UTF-8. Ese prehash evita el límite de entrada de 72 bytes de bcrypt sin truncar contraseñas largas; el valor original no se cifra ni se conserva y no puede recuperarse del hash. El formato se marca `bcrypt-sha256$2b$12$…`. Las credenciales históricas `scrypt` siguen verificándose y, tras un inicio de sesión válido, se reemplaza su hash por bcrypt con una actualización compare-and-set. La actualización es gradual: las cuentas que no vuelvan a iniciar sesión conservan temporalmente el formato anterior.
- Los refresh tokens deben ser aleatorios, almacenarse de forma revocable/hasheada en servidor y salir únicamente en cookie `HttpOnly`, `Secure`, `SameSite` según la especificación funcional.
- Las claves de firma, la contraseña bootstrap de PostgreSQL, la contraseña del rol de runtime, OpenAI y SMTP son credenciales separadas por entorno; no las compartas con staging. La API nunca recibe la contraseña bootstrap.
- Nunca registrar tokens, contraseñas, cookies, audio, texto privado de ideas o secretos en logs/telemetría.

## Sesiones de usuario

- La API firma JWT de acceso con HS256, `iss=grumphya-api`, `aud=grumphya-web`, `sub` UUID, `jti` UUID aleatorio por emisión y vencimiento de 10 minutos. `ACCESS_TOKEN_SECRET` es obligatorio y debe aportar al menos 32 bytes; se carga desde `.secrets/grumphya_env` en producción y el script local genera un secreto aleatorio en `.env.docker` ignorado por Git.
- El access token viaja en `Authorization: Bearer` y se conserva solo en memoria del navegador. Los endpoints de perfil, ideas aprobadas, contratación de plan y baja requieren firma válida y una fila de sesión activa en SQL.
- `GET /api/admin/dashboard` y `GET /api/admin/contact-messages` requieren una sesión activa y que el rol actual consultado en PostgreSQL sea `admin`; sin sesión responden 401 y con una cuenta normal responden 403. El acceso visual y la navegación no sustituyen esta autorización del servidor.
- Las rutas protegidas autentican con `Authorization: Bearer <accessToken>`. El refresh token no autoriza endpoints: es aleatorio, solo se entrega en cookie `HttpOnly`, `SameSite=Strict`, `Secure` en producción, `Path=/api`; la base almacena su hash. Cada refresh rota el refresh token y el hash del JWT activo. La migración `016_auth_refresh_rotation_history.sql` guarda el hash del refresh anterior a la última rotación en `previous_refresh_token_hash` (nunca el token claro); el siguiente refresh lo reemplaza. `POST /api/auth/logout` revoca la sesión con el hash actual o el inmediatamente anterior, para cubrir una llamada de logout que se solape con una rotación. Un token de dos o más rotaciones atrás no se acepta.
- «Recordarme» fija una vigencia máxima de 30 días desde el login. Sin marcarlo, la cookie es de sesión y la sesión caduca en servidor a las 24 horas. La rotación no amplía la fecha absoluta de caducidad.
- El navegador tiene una cookie de refresh compartida entre sus pestañas; iniciar sesión con otra cuenta sustituye la sesión de ese perfil de navegador. El aviso `session-changed` incluye un identificador de emisor para que la pestaña que lo publica ignore su propio eco; las demás limpian el access token en memoria y se recargan. No se pueden mantener cuentas distintas iniciadas en pestañas del mismo perfil; perfiles de navegador separados conservan sesiones independientes. Los datos y permisos de cada solicitud autenticada se asocian al usuario del access token validado en el servidor.
- La cuenta reservada Jappy se aprovisiona con un comando separado e idempotente. Repetirlo deja intacta una cuenta existente. El cambio de contraseña requiere el modo explícito `--change-password`, que también revoca sus sesiones activas. Un reinicio de API no toca la cuenta.
- La renovación concurrente comparte una sola petición dentro de la pestaña y el estado de logout no se restaura tras limpiar la sesión. El aviso entre pestañas sincroniza cambios de cuenta, no coordina ni serializa las renovaciones: si dos pestañas renuevan a la vez, el backend falla cerrado y una puede pedir iniciar sesión de nuevo aunque la otra conserve una sesión válida. La coordinación single-flight entre pestañas queda pendiente; este comportamiento no concede acceso a una sesión inválida.
- Login limita los intentos por IP, usa un mensaje genérico para credenciales inválidas y verifica hashes bcrypt actuales o hashes scrypt heredados. La actualización del hash de contraseña no cambia el hash SHA-256 almacenado para localizar tokens de sesión ni la firma HMAC-SHA-256 de los access tokens; son mecanismos distintos con propósitos distintos. Las mutaciones con cookie exigen `Origin` exacto y JSON; el borrado de cuenta también se limita y valida CSRF.

## Rotación y respuesta

Ante una exposición: revoca la credencial en su proveedor, genera otra, actualiza el archivo protegido correspondiente, reinicia/rota sesiones afectadas y revisa logs de acceso. Borrar un secreto del último commit no lo revoca: hay que rotarlo en origen.

No incluyas valores reales de contraseñas, claves, tokens, cookies de sesión o DSN privados en documentación, capturas o ejemplos. Usa nombres de variables o placeholders como `<secreto-configurado-en-el-VPS>`.
